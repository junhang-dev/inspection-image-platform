## 저장·원본 보존

- 시작 자료는 사진2/계획1/포인트0/논리 보수2. 종료 자료는 사진4/계획2/포인트0이며 QA가 계획1·사진2를 추가했다. 기존 5개 조회 개체와 각 이력은 기준 스냅샷과 동일했다.
- 최종 raw DB에서 QA 계획 version9/이력10, 첫 사진 version8/이력11, 둘째 사진 version4/이력7, 첫 보수 version5/이력6을 확인했다. API ID와 저장 ID를 대조했다.
- 두 새 사진 모두 입력 파일→원본 API 응답→MinIO 실제 객체의 크기·SHA가 일치했다. 메타데이터의 SHA 문자열만으로 보존을 판정하지 않았다.
- 사진 숨김/복원·계획 상태 변경·사람 등급·랙 수정 뒤에도 원래 전체 AI와 객체를 보존했다. 서버/DB/MinIO 재시작은 후보 A에서 실행하지 않았다.
- 로컬 원시 증거 54개를 파일별 SHA manifest로 묶었다. manifest SHA: `dd59fe6869b80b28d082bf75f10f3bc7f6fbbfc7ca4724de471be5d7d9970dad`. 원시 DB·로컬 경로·인증 값·개인 화면은 공개 기록에 포함하지 않는다.

## 실행 실패와 판정 한계

검증 하네스에서 중복 버튼 선택, API 상대 주소, 수집 코드 변수 오타를 수정했다. 해당 실패는 변경 요청 전에 발생했고 임의 재업로드로 복구하지 않았다. 브라우저가 about:blank로 바뀌고 이후 CLI 세션이 닫힌 일이 있어 같은 저장 ID를 재조회한 뒤 이어갔다. 제품 원인으로 확정하지 않는다. console의 최초 favicon404와 세션 생성 전 상태 조회404를 실제 업로드 실패와 구분했다.

- receiving 중 계획 종료→재개 후 같은 세션 완성, 전송 응답 유실/부분 실패의 UI 복구는 A에서 새로 재현하지 않았다. 제품 담당 HTTP trace와 이전 v2 검사만으로 이 행을 독립 PASS로 승격하지 않는다.
- 기존 계획 미지정/포인트 관계가 있는 원본 자료의 재연결·이관, 전체 원본300/299객체 보존, 재시작 보존은 후속 B의 별도 증거가 필요하다.
- ROI/SHAP 경합·표시·삭제/복원은 후속 B 대상이다. A의 알려진 ROI 후속 수정이 이 기록으로 통과한 것은 아니다.
- 고정 주소·외부 쓰기/재시작은 배포 담당의 별도 검증이다. A는 로컬 격리 후보이며 공유 서비스로 전환하지 않았다.
- 모델 정확도 FAIL은 그대로 유지한다. 사람의 전체 업무 시간, 새 최종 test, 현장 안전 판단/설명 타당성, 실제 동료 검수는 이번 실행으로 증명하지 않는다.

이 기록은 [v3 검증 계약](../docs/validation-v3-contract.md)의 실제 실행 부분을 채운다. 모든 22개 행과 W01~W16의 전체 완료로 확대하지 않는다.
