- 구현·검증일: 2026-09-21 KST.
- 범위: 업로드의 10장/20MB 제한 제거, 파일별 큐와 재시도·새로고침 복구, 원본을 보존하는 디스크 수신, 동결 모델 스트리밍 입력 통합. 공개 demo 선택 버튼과 업무 화면의 내부 서버 설명을 제거한다.

## 구현과 검토

전송 ID에 전체 원본 SHA·크기·이름·계획/포인트를 고정한다. 서버는 고정 검사 UUID와 원본 객체 키를 사용하며, 4MiB 청크를 디스크에 받아 검증·fsync한 뒤 확정 offset을 기록한다. 동일 청크 재시도는 길이와 SHA가 같은 경우만 성공한다. 원본 객체·DB 저장의 응답 손실 뒤에도 같은 UUID로 복구하며 사진·등록 이력·세션 완료를 한 트랜잭션으로 확정한다.

브라우저 파일 목록과 서버 저장 여부를 분리한다. 새로고침 후 서버 결과를 먼저 확인하고 남은 파일만 원래 파일 재선택과 전체 SHA 확인 후 이어 전송한다. 저장 완료와 AI 판독 완료를 따로 표시하며 한 파일 실패 뒤에도 다음 파일은 처리한다. 이미 만든 계획·포인트를 업로드 실패로 제거하지 않는다.

독립 검토가 발견한 연결 풀 교착 가능성, Sharp 스트림의 전체 입력 버퍼 보관, 디스크 여유 확인 전 원본 연결이 끊길 때의 잡히지 않은 오류를 수정했다. 관계 검증은 이미 보유한 DB 연결을 재사용하고, 썸네일도 디스크 경로에서 생성하며, 원시 수신·청크의 스트림 오류 처리를 첫 비동기 대기 전에 연결한다. 일반 multipart에는 안정된 파일별 ID가 필요하다. 느린 청크 요청이 공용 DB 연결을 모두 점유하지 않도록 연결 획득 전에 동시 수신을 4개로 제한한다. 독립 재검토에서 이 범위의 미해결 P1/P2는 없었다. 임시 파일 정리는 세션 잠금/활성 원시 수신을 고려하고 원본 객체·완료 DB 이력을 삭제하지 않는다.

## 실제 검증

- 타입 검사·후보 프로덕션 빌드 통과. 전체 단위/API 회귀 검사 29개를 통과했으며 API 입력 보호 검사 6개는 새 격리 API를 대상으로 실행했다.
- 장애 주입 단위 검사 8개 통과: 부분/다른 내용의 청크, 잘못된 offset·파일 identity, 청크 COMMIT 전 실패와 응답 손실, 객체 저장 뒤 응답 손실과 DB 실패, 동시 최종화·최종 COMMIT 응답 손실, 다른 내용의 기존 객체 덮어쓰기 차단, 만료/재시작, 수신 직후/도중 단절의 임시 파일 정리, 느린 청크 4개 수신 중 추가 요청 503 및 중단 후 수신 슬롯 반환. DB/객체 장애는 통제된 모의 구현이며 실제 MySQL 장애를 일으킨 검사가 아니다.
- 첫 단위 검사 실행은 테스트용 SQL 모의 코드가 DELETE를 SELECT로 잘못 분기해 1개 실패했다. 해당 모의 분기를 바로잡아 재실행했으며 실제 제품의 재시작 검사와 별도로 남겼다.
- 실제 격리 MySQL·MinIO·API에서 포인트에 연결하는 서로 다른 세션 8개를 동시에 생성했다. 59ms에 모두 성공하며 중첩 연결 풀 대기가 없었다.
- 실제 API에서 부분 청크는 422/offset 0, 같은 청크 재요청은 200, 내용 변경 청크와 같은 ID의 다른 원본 계약은 409였다. 같은 사진의 동시 완료 요청 2개가 같은 UUID를 반환했고 등록 이력은 1개, 다운로드 원본 SHA는 입력과 같았다. 잘못된 이미지의 최종화는 422이며 사진으로 등록되지 않았다.
- 회사 자료와 무관한 **25,273,574바이트 PNG**를 생성했다. 첫 4,194,304바이트를 확정한 뒤 API 컨테이너를 교체했다. 동일 임시 볼륨의 offset·검사 UUID를 보존하고 남은 바이트를 전송했으며, 저장 원본 다운로드 SHA·썸네일 응답·실제 동결 모델 판독을 확인했다. 합성 이미지 등급은 모델 성능 평가에 사용하지 않았다.
- 제품 Compose에서 새 모델 named volume을 root 초기화 도구 없이 연결했다. 실제 TMPDIR `/uploads-tmp`, UID/GID 10001, 모드 0700, 임시 파일 쓰기/fsync/읽기/정리를 확인했다.
- 이 API 검사 전의 사진 15장·포인트 31개·계획 9개 전체 메타데이터와 각각의 전체 변경 이력이 동일했다. 추가 검증 자료는 기존 자료와 ID로 구분했으며 운영 공유 서비스에는 쓰지 않았다.

## 독립 브라우저 검사와 공유 반영

- QA는 격리 웹 후보 `IH4Hic5nFa25IVgE76ubE`와 API r2에서 12개를 한 번에 선택했다. 승인 demo 복제본 11개와 패딩 없는 3072×3072 합성 PNG 28,323,297바이트다. 이후 긴 이름의 별도 신규 사진 1개를 추가해 13개, 총 63,903,969바이트를 검증했다.
- 첫 청크 503, 실제 저장 뒤 complete 응답 손실과 조회 실패, 대용량 첫 4MiB 뒤 실패를 브라우저에서 제한적으로 모의했다. 다음 파일 전송, 같은 ID 재시도, 새로고침 뒤 이미 완료한 UUID 복구, 원래 파일 재선택과 offset부터 재개를 확인했다. 크기가 다른 파일 재선택은 거절했다. 같은 크기/다른 내용 재선택의 실제 브라우저 검사는 하지 않았다.
- 13개 각각 입력 파일·DB 메타데이터·API 다운로드·MinIO 직접 원본의 크기/SHA가 일치했고 실제 AI는 모두 완료했다. DB 행은 UUID마다 1개, 등록·판독 시작·완료 이력은 각각 1개였다. 두 UUID의 동시 완료 재요청은 이력과 세션을 바꾸지 않았다. 기존 사진 17개의 모든 응답 필드가 유지됐다.
- QA가 390/768/1366/1440px에서 선택·실패 큐, 긴 이름, 파일 재선택 버튼, 필터 `1장`/`미조회`를 확인했다. 문서/모달의 가로 넘침·버튼 잘림은 없었다. 후속 검토의 두 표시 문제는 저장 큐의 오래된 AI 상태 문구를 저장 사실과 목록 확인 안내로 바꾸고, 재선택 입력을 한 줄 버튼으로 조정했다. 이 두 변경은 별도 좁은 화면 검사로 확인한다.
- API r2에서 r3으로 바뀐 파일은 `server/uploads.mjs` 하나로, 수신 네 개의 admission 보호다. 제품 담당이 실제 느린 HTTP 청크 4개를 유지한 동안 다섯 번째 503과 health 200을 37.45ms에 확인했다. 연결 중단 후 슬롯이 반환되고 정상 청크가 200/offset 진전으로 끝났다. 원래 13개 업로드를 반복하지 않았다. 최종 r3 이미지는 `sha256:8d97bdad51d68b8d8eb4718ae0a3a7c0560256fd5b01f5211c7e7b7cdab3e9e3`다.
- Mac 모델은 별도 소스 아티팩트에서 `--check`로 동결 식별자를 확인했다. 기존 8001과 새 임시 18001에 같은 승인 demo 1장을 실제 판독해 등급 4, 점수 0.9960895776748657 및 모델/전처리 버전이 정확히 같았다. 새 Mac 경로의 25.27MB 합성 원본도 판독됐다. 고정 test를 읽거나 재실행하지 않았다.
- 23:13 KST 같은 공유 주소에 웹·API·모델 입력 경로를 전환했다. 공개와 로컬 루트/health는 200, 새 빌드·동결 모델/전처리/가중치 SHA를 확인했다. 청크 CORS 사전 요청은 204였다. 전환 중 기존 웹의 API 연결이 잠시 끊겼으며 완료 후 정상 응답을 확인했다.
- 운영 사진 64장·포인트 4개·계획 4개의 모든 메타데이터와 전체 변경 이력이 정확히 유지됐다. 기존 원본 64장을 다시 다운로드한 검사는 아니며 SHA/크기 메타데이터를 비교했다. 공개 검증용 새 데이터 쓰기는 없었다.
- 배포 담당은 23:15:39 KST 공개 HTML 실바이트와 운영 아티팩트의 일치, 실제 포트·프로세스·모델 식별자·상태 응답을 독립 확인했다. 제품과 이전 HTTP 모델의 별도 소스/실행 명령을 롤백용으로 보존했다. 모델 이전 소스는 허브가 Git blob과 독립 대조했다.

- 마지막 두 UI 조정은 후보 `VKN6YkBI0RQQdShLOqjKj`에서 기존 13개 큐의 명확한 저장 안내, 390px 재선택 버튼 한 줄 표시·파일 재선택·키보드 포커스를 QA가 확인했다. 추가 사진 전송/추론 없이 기존 13개 저장 상태를 유지했다.
- 23:20 KST 웹만 최종 공개 빌드 `qcsQTq-_XDX_JXq_4Qn9M`으로 전환했다. API r3·모델·DB·객체 저장소·터널은 유지했고 공개/로컬 HTML 빌드와 health 200을 확인했다. 최종 웹 소스와 root의 런타임 파일 16개는 SHA가 같으며, API는 같은 서버 소스 바이트의 기존 프로세스를 유지했다. 배포 담당은 23:22:13에 최종 웹의 공개/로컬 HTML 실바이트·아티팩트·새 PID/실행 경로를 독립 확인했으며 API/모델 검사는 앞선 23:15:39 결과와 구분해 보존했다.

## 범위와 한계

전송 ID와 실제 응답·원본 SHA 등 상세 증거는 로컬 전용 기록이다. 회사 원본 300장·고정 test·가중치·DB·비밀은 공개하거나 build context에 포함하지 않았다. 고정 test 정확도 60%/목표 70% 미달은 그대로이며 새 입력 경로 기능 검증으로 모델 성능을 통과 처리하지 않는다.

글자 크기·대비·필터 건수 배치는 독립 CSS 변경이다. 후속 보수/워크리스트 개편, 숨김·복원, 목적별 집계, 보강 지도는 이번 업로드 단위와 구분한다. 비개발자 동료의 실제 전체 흐름 검수와 시간 측정은 아직 별도다.
