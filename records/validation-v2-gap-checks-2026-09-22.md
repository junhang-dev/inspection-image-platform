10장·숨김·후보 해제는 2026-09-22 02:01~02:14 KST에 기존 격리 Flow 후보에서 직접 실행했다. 네이티브 파일 선택창은 같은 날 07:09 KST 이후 별도로 확인했다. 공개 서비스 배포나 모델 정확도 합격을 뜻하지 않는다. 뒤에 다른 담당이 완료한 R15·판독 실패 검증과 구분한다.

## 처리 중 숨김과 늦은 AI 완료

새 묶음 중 한 사진의 실제 `processing` 상태를 확인하고 버전 조건으로 숨겼다. 같은 ID 이력은 업로드 → 실제 백그라운드 판독 시작 → 처리 중 숨김 → 실제 판독 완료 순서였고, 최종값은 `done`·`hidden`이었다.

일반 사진 목록 9장, 숨김 포함 목록 10장, 대시보드 전체 사진·보수 필요 분류 각 9장, 해당 랙과 포인트의 지도 사진 수 9장을 확인했다. 숨김 사진의 원본 API는 404였고 MinIO 원본은 보존됐다. 표시 사진 9개의 실제 API 다운로드와 숨김 포함 MinIO 10개를 직접 읽어 입력 크기·SHA와 모두 일치했다. 최종 화면을 캡처한 뒤 직접 열어 확인했다.

이 묶음 전후 기존 4장의 개별 사진·전체 이력, 기존 보수 기록·이력과 다운로드 결과는 동일했다. 새 사진 10개·포인트 1개·계획 2개가 추가됐으며 기존 QA 기록을 덮어쓰지 않았다. 지도 캡처의 축약된 exact 접근성 이름 검사 `kpi:0`은 선택자 불일치였고, 실제 화면·본문의 9장 표시와 목록·API 결과로 확인했다.

## 재촬영·라벨링 후보 해제

이전 연속 흐름의 QA 사진 한 장을 해당 계획으로 제한해 재촬영·라벨링 목록에서 조회하고 두 표시를 각각 UI로 해제했다. 재촬영 해제 뒤 재촬영 목록에서 제외되고 라벨링 후보에는 남았다. 라벨링 해제 뒤 후보 목록에서도 제외됐다. 각 최종 목록은 0장이었다.

사진의 version은 1→2→3이며 변경된 필드는 재촬영·라벨링 플래그, 수정 시각·버전뿐이다. 원래 AI, 사람 등급 null, 기존 재촬영 사유, 계획·포인트 연결, 원본 식별자·해시, 보수 기록과 보수 이력은 그대로였다. 기존 사진 이력 4개를 보존하고 수정자·시각·사유·전후 값이 있는 해제 이력 2개만 추가했다.

첫 자동화는 화면 전환 후 상태 필터가 `all`로 초기화된 것을 놓쳐 일반 목록에서 사진이 사라지기를 기다리다 timeout이 났다. 실제 재촬영 해제는 이미 저장됐으므로 재저장하지 않았다. 필터를 `retake`로 다시 적용해 제외를 확인하고 같은 사진에서 남은 라벨링 해제를 완료했다. 이 결과는 필터를 복구한 기능 검증이며 중단 없는 시간 측정이 아니다.

## 손상 파일과 별도 담당 인계

회사 데이터가 없는 57bytes 합성 손상 JPEG를 같은 QA 묶음 문맥으로 한 번 전송했다. 응답 대기 경로를 실제 `/api/upload-sessions/{id}/complete`와 다른 경로로 작성한 하네스 오류 때문에 이 실행 영수증은 timeout으로 남았다. 이 영수증만으로 거절 성공을 판정하지 않았고 새 업로드로 반복하지 않았다.

대기 중 허브·제품 담당이 별도 격리 환경에서 손상 파일의 실제 422·사진 미생성, 실제 모델 연결 실패 후 UI 재시도 한 번·동일 사진 ID·실제 모델 결과 및 원본·이력 보존을 검증하고 결과를 회수했다. R15의 원본 등록·지도 검증도 별도 담당 결과다. 이 문서는 그 검사를 본 QA가 직접 다시 실행했다고 주장하지 않는다.

## OS 파일 선택창 직접 표시·취소

브라우저 filechooser 이벤트·파일 지정·실제 저장은 기존 증거다. 07:09 KST 이후 네이티브 도구 응답을 받아 기존 QA 창의 선택 가능 여부를 확인했다. 최초 앱 접근은 QA 전용 프로세스와 다른 일반 사용자 창을 반환했고 지원되는 Chrome 연결 목록에도 기존 QA 탭이 없었다. 해당 사용자 탭은 조작하지 않았다. 기존 QA 브라우저·API는 살아 있었지만 웹 listener가 없음을 확인했다.

허브와 조율한 뒤 기존과 동일한 BUILD의 격리 QA 웹만 복구했다. API·DB·MinIO·모델을 재시작하거나 제품을 다시 빌드하지 않았다. 브라우저 도구의 새 탭 생성은 `Owl extension-created tabs must be active`로 실패했고, 표시 옵션은 `Capability is not available: visibility`로 실패했다. 이는 탭 생성 도구의 실패이며 OS 창 표시나 업로드 기능의 실패가 아니다.

이후 지원되는 네이티브 Cua의 새 창 단축키로 **새 QA 전용 Chrome 창**을 만들고 격리 QA 주소를 입력했다. 정확한 URL과 PlantPilot 제목을 확인한 다음 사진 업로드 → 검사 사진 선택 버튼을 눌렀다. 실제 macOS `open-panel`의 파일 목록·열기·취소 버튼을 스크린샷과 접근성 트리에서 직접 확인하고 **취소 버튼을 클릭**했다. 취소 뒤 같은 업로드 창에 선택된 파일 없음, 전송 버튼 비활성, 전송 큐 항목 없음이 유지됐다. 파일을 선택하거나 전송하지 않았으며 새 판독도 실행하지 않았다. 검증 후 직접 만든 전용 창만 닫았다.

취소 전후 API의 사진·포인트·계획·보수 응답이 모두 동일했다. DB 전체 4개 테이블을 읽어 행을 정렬한 뒤 개수·SHA-256을 비교했으며 entity 29개, history 70개, upload session 15개, chunk 15개의 값·개수·해시가 모두 동일했다. 기존 손상 파일 시도의 session/chunk도 그대로 보존됐다. 따라서 **실제 OS 선택창 표시 및 취소 후 영속 부수효과 없음은 PASS**다. 네트워크 쓰기 요청 개수를 별도로 계측하지 않았으므로 `POST 0건`을 관측했다고 표현하지 않는다. 실제 선택창의 다중 파일 선택 시각 조작은 이번 취소 검사에 포함하지 않는다.

이 검사는 Google Chrome에서 직접 수행했으며 별도 Chromium revision으로 바꾸거나 보안·권한 설정을 변경하지 않았다. 최초 기존 창 연결 실패와 새 전용 창에서의 최종 성공을 구분한다.

원시 영수증·ID·요청·해시·화면은 Git 제외 로컬 증거와 허브 인계 묶음에 보존한다. 공개 문서에 회사 원본·인증 정보·내부 경로를 넣지 않았다. 본 결과로 기존 모델 최종 test 60%와 목표 70% 미달을 바꾸지 않는다.
