## 실제 모델을 포함한 전체 기능 흐름

빈 Flow 환경에서 새 검증용 계획·포인트를 만들고 승인된 `demo-01.jpg` 한 장을 실제 파일 선택기 이벤트로 지정했다. 업로드→실제 AI→원래 등급 유지→재촬영·라벨링 후보 표시→보수 상태/방법·TA·워크리스트 명시 저장→워크리스트에서 같은 기록 재열기→사유·이력을 확인했다. 두 번째 실행도 별도 계획·포인트를 사용했으며 중단된 업로드는 같은 전송 ID로 복구했다. 최종적으로 계획·포인트·사진·보수 기록이 각각 두 개다.

두 사진 모두 실제 모델 결과는 4등급이며 모델 `mobilenetv3small-ft-20260921T074822Z`, 전처리 `rgb-first-frame-exif-full-resize224-imagenet-v1`가 응답에 남았다. 사람 수정 등급은 null로 유지했고 재촬영·라벨링 판단과 별도 보수 기록을 저장했다. 보수는 작업 예정/도장/워크리스트 등록/TA 포함이다. 이것은 실제 연결·저장 기능 증거이며 두 사진으로 모델 정확도를 평가하지 않았다. 기존 고정 test 정확도 60%와 목표 70% 미달은 변하지 않는다.

시연 입력은 2,965,056bytes, SHA-256 `0510d0827704d8ec297bdecdebfd2eb7f65c44521e662fa8532036e47a610838`다. 브라우저 file chooser 이벤트와 CLI 파일 지정을 확인했으며 OS 선택기 화면 자체를 시각적으로 검수한 것은 아니다.

## 시간 계측과 자동화 오류

초기 대표 흐름 두 시도의 총 시간은 각각 **213.820초, 155.922초**다. 자동 검증 스크립트의 실패·확인·재개가 포함돼 있으므로 이 두 시도로 약 1분 완료 조건을 판정하지 않았다. 사람의 실제 판단·입력 속도 측정도 아니다. 후속 연속 측정은 아래에 별도로 기록한다.

- 첫 시도: 파일 input이 덮고 있는 안내 문구를 선택해 클릭 대기, 업로드를 닫은 뒤 다시 나타난 계획 상세를 닫지 않은 채 탐색 시도, 숨김 관리 폼과 판단 폼의 같은 input name을 구분하지 못한 선택자 오류가 있었다. 실제 file input·대화상자·접근성 이름으로 보정하고 같은 기록을 이어서 완료했다.
- 두 번째 시도: 복구 목록에 남아 있는 첫 사진의 완료 안내를 새 전송 완료로 오인해 업로드 창을 조기 닫았다. 새 계획에 사진이 없는 것을 확인한 뒤 동일 전송 ID에서 원본을 재선택해 복구했다. 새 사진을 추가로 중복 생성하지 않았다.
- 두 번째의 최초 `original_stored`와 그 뒤 빈 목록을 기다린 약 46.9초 구간은 잘못된 측정 마커다. 이를 AI 대기로 차감하지 않는다. 복구 후 실제 pending→done만 기다린 구간은 약 0.519초였다. 첫 시도는 실제 AI 완료 뒤에 결과를 확인했으므로 모델 처리 시간을 별도로 빼지 않는다.

기본 보수 검사에서도 처음의 중복 select 선택자와 계획 상세 닫기 누락을 보정했다. 독립 API 캡처 스크립트는 경로 구분자 누락으로 404가 발생했으며, 생성되지 않은 before 파일을 인계했다고 먼저 알린 메시지를 즉시 정정했다. 이를 완료 증거로 사용하지 않는다. 제품 담당이 실제로 생성한 원시 before와 후속 독립 비교를 구분해 기록한다.

## 재시작 보존

Flow 첫 사진을 UI에서 명시적으로 숨겨 version2로 만들었고, 해당 보수 기록의 근거 연결은 유지했다. 두 번째 사진은 version1·표시 상태다. 이 숨김 작업은 대표 흐름 시간에 포함하지 않았다. 제품 담당이 실제 before 자료를 생성한 뒤 격리 웹/API/MySQL/MinIO를 정상 재시작했다. QA가 그 before/after 원시 자료를 독립 대조한 결과 entity 8개·history 17개·upload session 2개·chunk 2개가 완전히 같았다. 재시작 후 직접 읽은 API 16개 응답에서도 사진·포인트·계획·보수 기록의 ID·값과 모든 이력이 기준과 일치했다.

표시 사진의 API 원본을 직접 다운로드해 입력 SHA와 비교했고, 숨긴 사진의 원본 API는 404였다. 두 MinIO 객체를 각각 직접 읽어 모두 2,965,056bytes와 위 입력 SHA가 같음을 확인했다. 제품 담당의 재시작 전 실제 객체 해시 기록과도 일치한다. QA의 실패한 before 다운로드 캡처를 이 근거에 포함하지 않는다.

브라우저에서는 작업 예정/도장/TA 포함 조건에서 두 보수 기록, 교체 또는 완료 조건에서 0건을 확인했다. 첫 보수 기록의 숨긴 근거 사진 선택과 상태·방법·TA·등록값이 유지됐고, 숨긴 사진 상세의 AI/사람 값·재촬영·라벨링·숨김 사유와 이력을 다시 확인했다. 이력 응답 전의 첫 캡처는 미완성 증거로 남기고 실제 이력 로딩 후 다시 캡처했다.

**D10의 서버 기록·이력·원본 보존은 해당 두 기록에서 PASS다.** 재시작 뒤 새 브라우저 프로필에는 이전 localStorage 큐가 없어 UI 전송 목록 복구를 이 검사의 PASS에 포함하지 않는다. 서버 session/chunk 두 개의 완전 보존과 두 번째 전송의 재시작 전 동일 ID 복구는 각각 실제 확인했다.

## 증거와 남은 범위

기본 UI 모의는 모두 해제했고 두 검증 브라우저를 닫아 제품 담당에게 슬롯을 반환했다. 증거에는 요청·응답·버전·원시 비교 결과·자동화 실패 로그·viewport 스크린샷이 포함된다. 상세 ID와 로컬 경로는 Git 제외 증거에 보존하며 공개 문서에는 내부 경로·인증 자료·원시 회사 데이터를 넣지 않는다.

최초 legacy 이관과 경합 순서 전체, 미조회 timeout, 신규 보수 저장 실패는 제품 담당의 실행 범위 또는 미검증으로 남긴다. 이 기록은 새 보수 기능과 실제 모델 연결을 확인하며 전체 v2의 미검증 항목이나 대표 시간 조건을 자동으로 완료하지 않는다. 재시작 후 마지막 읽기 검증에서도 새 자료나 추가 이력을 생성하지 않았다.


## 후속 연속 자동 조작 측정

2026-09-22 01:51 KST, 같은 Flow 후보에서 승인 demo 한 장과 별도의 새 계획·포인트를 사용해 단일 `run-code`를 중간 개입 없이 실행했다. 최종 실행 코드 SHA-256은 `7a86360ff8846cf939318740038094cfcd71b09b4312d5b245293e9cbe50d59c`이며 결과는 `COMPLETE_CONTINUOUS_AGENT_OBSERVATION`이다.

| 측정 구간 | 실제 관측값 |
|---|---:|
| 첫 계획 탐색부터 원래 계획의 같은 사진·이력 재조회까지 | 3,969.700ms |
| 새 사진의 AI 결과만 기다린 구간 | 1,297.500ms |
| AI-only 대기를 뺀 업무 흐름 | **2,672.200ms** |

같은 문서의 `performance.now()`로 15개 단계 이벤트를 남겼다. 종료−시작, AI-only 차감, 이벤트 순서를 독립 재계산해 일치함을 확인했다. 계획 생성→포인트 생성·연결→파일 지정·전송→실제 AI→원래 AI 유지 및 재촬영 사유·라벨링 후보 저장→작업 예정/도장/TA/워크리스트 저장→보수 이력→원래 계획의 같은 사진·이력 재조회가 포함된다. 예상 업무 저장 요청 7개는 각각 한 번, 청크 PUT은 한 번이었다. 계획·포인트·업로드·사진·보수 UUID를 응답부터 연결해 이전 완료행이나 최신 사진으로 대신하지 않았다.

**자동 조작 조건에서는 AI 대기를 제외한 업무 흐름이 60초 이내로 관측됐다.** 파일은 `setInputFiles`로 지정했으므로 OS 파일 선택창을 열어 파일을 찾는 시각 조작 시간, 사람의 판단·입력 시간은 포함하지 않는다. 자동 타이머의 전체 Done 판정은 null로 유지했고 이 조건의 관측 결과만 보고한다. 기존 실제 file chooser 이벤트 검증은 별도 증거이며 그 시간을 이번 수치에 합산하거나 대신 측정했다고 하지 않는다.

이 실행 전 사전 검사 두 건은 URL 전역 부재와 UI API origin 설정 차이를 발견하고 쓰기 0·타이밍 없음으로 종료했다. UI는 웹과 같은 출처의 `/api` 프록시를 사용하므로 측정은 그 실제 출처를 지정하고, 사후 독립 조회는 격리 API로 직접 수행했다. 이후 한 실행은 업로드 직전 `getByLabel`의 exact 이름 불일치로 중단됐다. 해당 타이밍은 null로 보존하고 생성된 같은 계획·포인트에서 업무 기능만 복구했다.

실제 화면을 보는 QA가 하네스 편집을 맡아 남은 두 선택자를 정확한 combobox 역할로 바꾸고, 사진 수정자·사유·워크리스트 카드의 단일 매칭을 실제 DOM에서 대조했다. 제품 코드는 바꾸지 않았다. 문법 검사 네 개와 제한된 VM 계약 네 개를 통과한 후 별도의 새 세션·새 ID에서 위 유효한 연속 실행을 수행했다. 이전 시도를 다시 시작하거나 복구 시간을 빼서 성공으로 바꾸지 않았다.

기능 복구 한 건과 유효한 연속 실행 한 건으로 Flow의 사진·계획·포인트·보수 기록은 각각 네 개가 됐다. 각 추가 원본은 입력/API 실제 다운로드/MinIO 직접 읽기의 크기 2,965,056bytes와 승인 demo SHA가 일치했다. 유효한 실행 직전 기존 세 기록의 값·전체 이력·원본 응답은 실행 후에도 같았다. 두 추가 사진 모두 실제 동결 모델 판독 이력, 사람 등급 null, 후속 판단과 보수 이력을 확인하고 스크린샷을 직접 열어 봤다. 모든 사용 브라우저를 종료했으며 완료 큐와 실패 영수증은 로컬 증거로 보존했다.

기존 D10 결과는 재시작 당시 두 기록의 증거다. 뒤에 추가된 두 기록으로 재시작을 반복하지 않았으며, 이들을 이미 D10 검증한 것처럼 합산하지 않는다. 모델 정확도 미달과 전체 v2의 다른 미검증 범위는 그대로다.
