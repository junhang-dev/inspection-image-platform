# 검사 계획 중심 작업 흐름 v2 · 첫 단위

- 시작 기준: `c157cd5cd2954d3041c52200c39ff2b5f848daf8`
- 구현·검증일: 2026-09-21 (KST)
- 목적: 계획을 만든 뒤 검사할 포인트를 연결하고, 그 계획의 사진만 업로드·조회한다. 같은 포인트를 여러 계획에서 검사해도 사진이 섞이지 않게 한다.
- 제품명: PlantPilot / 플랜트파일럿 · 검사·보수 통합 관제.

## 구현

- 정유1~4팀과 팀별 파이프랙에 고정 가상 ID를 부여했다. 새 포인트는 선택된 랙 ID와 가상 상대 위치를 저장한다. 실제 팀 경계나 실측 위치를 뜻하지 않는다. 기존 미확인 포인트는 임의로 배치하지 않는다.
- 계획은 `pointIds`를 가지며 기존 단일 `pointId` 입력과 저장 자료를 호환한다. 기존 연결을 제거하지 않는 추가 방식과 수정 버전 검사를 함께 적용했다.
- 사진은 `planId`와 `pointId`를 함께 저장하며, 서버가 계획에 속한 포인트인지 검증한다. 기존 사진은 `planId: null`로 읽고 날짜·이름으로 과거 계획을 추정하지 않는다.
- 계획 생성 후 상세 창을 열고 기존 포인트 연결, 선택 팀·랙에 새 포인트 등록, 해당 계획·포인트로 사진 추가를 이어간다. 계획별 조회는 서버에서 제한 적용 전에 필터링한다.
- 새 포인트 등록이 성공한 뒤 계획 연결이 실패하면 생성된 포인트와 입력을 보존한다. 사용자가 연결 확인·재시도를 선택하면 최신 계획을 조회하고, 이미 연결된 경우 중복 저장하지 않는다.
- 원래 사진 포인트가 목록에서 누락돼도 현재 ID를 보존한다. 알려진 가상 랙은 이름만 수정할 수 없으며 UI와 API에서 명확하게 처리한다. 사진 조회 실패는 확인된 0장과 구분한다.

## 실제 검증

- 타입 검사와 Node 문법 검사 통과.
- 저장·관계 단위 검사 9개 통과. 기존 계획 읽기 호환, 사진 계획 미추정, 팀별 랙 ID·가상 위치, 계획 필터의 SQL 적용 순서와 기존 CAS·AI 병합 계약을 확인했다.
- 독립 소스 검토 지적 3개를 수정하고 재검토에서 해당 범위의 새 차단 문제가 없음을 확인했다. 이는 코드 검토이며 브라우저 실행 검증과 구분한다.
- 별도 DB·객체 저장소에서 실제 API 검증 6묶음 통과. 검증 전 사진 11장·포인트 25개·계획 5개의 기존 값과 모든 변경 이력을 보존했다. 검증 후 각각 13장·27개·7개다.
- 같은 표시 이름의 다른 팀 랙이 구분되고 동일 랙·설비·이름 재요청은 기존 포인트를 반환했다. 상충하는 랙 이름 수정은 422, 기존 계획 연결 제거·없는 포인트 연결은 422, 오래된 계획 수정 버전은 409이며 실패로 인한 데이터·이력 변경이 없었다.
- 승인된 시연 사진 1장을 같은 포인트의 서로 다른 두 계획에 업로드하여 서로 다른 사진·원본 객체를 얻었다. 계획별 조회는 각각 자기 사진 1장만 반환하고, 시연 재사용도 계획 범위를 지켰다. 기존 계획 미지정 사진 11장은 그대로 남았다.
- 계획에 속하지 않은 포인트 업로드 및 사진 연결 수정은 422로 거절했다. 사람 등급 수정 후 원래 AI 결과와 계획·포인트 관계가 보존됐다.
- 새 사진 2장에 연결된 동결 모델의 실제 추론이 완료됐고, 다운로드한 두 원본은 승인된 샘플의 바이트 크기·SHA-256과 같았다.
- 첫 API 검증 시도에서 MySQL JSON의 부동소수점 표현 차이 약 `3e-17`을 정확 비교하여 중단됐다. 검증 기준을 `1e-12` 허용오차와 반복 조회의 정확 일치로 수정하고 같은 두 포인트를 재사용했다. 제품 오류를 숨기거나 자료를 삭제하지 않았다.
- 후보 웹 빌드와 HTTP 루트·API·모델 연결 확인을 완료했다. 계획 상세의 포인트별 사진 수·사진 표를 실제 브라우저에서 확인했다.
- 독립 브라우저 검증 통과: 계획 생성 후 자동 상세, 선택 팀·랙을 상속한 새 포인트, 다른 랙 기존 포인트 연결, 같은 포인트의 두 계획에 실제 사진 각 1장 업로드·필터 분리, 기존 미지정 사진 보존을 확인했다.
