## 실제로 발견한 변경 경계

| 기존 동작 | 새 요구에 맞춰 확인할 위험 |
|---|---|
| 계획 생성의 포인트 목록은 이미 빈 값 가능하지만 계획에 사진을 넣을 때 포인트 필수 | 계획 작성과 업로드의 관계 제약을 구분. 팀·랙 직접 관계와 기존 pointId 보존 |
| 계획 없는 업로드 허용, 계획 PATCH는 상태·포인트 추가 중심 | 새 무계획 거절·일반 수정·삭제/복원·전송 중 상태 변경 정책 |
| 가상 4팀×3랙, 사진 필터가 포인트의 랙으로 팀을 찾음 | 30랙 확장과 포인트 없는 사진의 필터 누락·팀-랙 혼합 방지 |
| 보수 ID는 계획+필수 포인트이며 명시 저장/포함 | 자동 업무 식별 단위·이관, 사람 제외·완료 보수 우선순위 |
| worker는 원본을 동결 모델에 연결하고 사람 값과 추론 값을 분리 | ROI revision·설명 job·모델 해시 결합, 오래된 결과 차단, 설명 실패 격리 |
| SHAP/ROI 전용 흐름은 읽은 제품 `server/`·`src/` 기준에서 확인되지 않음 | 신규 계약과 실제 설명 실행 증거 필요. 다른 작업의 준비 코드 부재까지 주장하지 않음 |
| 목적 입력·포인트 탐색·펼친 이력과 PlantPilot 이름 | 화면 제거와 기존 데이터/공개 경계 보존을 구분 |
| 운영 복구 때 임시 URL이 바뀐 실제 v2 이력 | 고정 제출 URL은 재기동 전후 같은 URL의 신규 증거 필요 |

[검증 계약](../docs/validation-v3-contract.md)에 V3-01~22의 변경·회귀 행렬, C01~12의 미확정 정책, 최소 수직 흐름·실패/경합·원본 보존·고정 URL 영수증을 작성했다. 후보가 없어 기존 서비스/PW 세션은 조작하지 않았고 개인 파일 목록·회사 원본 화면을 수집하거나 공개하지 않았다.

허브 product-v3 초기 계약과 제품 초기 제안 회신을 읽고 W01~W16을 V3 항목에 대응했다. 계획 필수·포인트 선택적·팀30랙·종료 후 재개·실험자료 격리·사용자 ROI·M1~M5 방향은 반영했다. 전송 중 종료 경합409와 같은 세션 복구 등은 제품 제안으로 구분한다. 초기에는 포인트 없는 자동 업무의 단위가 허브의 사진ID별 기본과 제품의 계획+랙 검토안 사이에 달라 정책 충돌로 전달했다. 이후 허브가 사진ID별 자동보수1개로 확정하여 C05 대기를 해제했다. source photo 안정 키로 중복을 막고 계획/랙은 조회그룹이며, 기존 계획+포인트 업무는 원ID·상태·이력을 보존한다. 이 계약의 구현·실행은 여전히 미검증이다. 상세 상태/삭제 전파/모델·SHAP/고정 URL 계약은 확정 대기를 유지한다. 준비 문서 작성 자체를 v3 기능 완료나 모델 성능 향상으로 표시하지 않는다.

대조한 허브 `docs/product-v3.md` 내용 SHA-256은 `202cd7c0800c7bebdde83763408120bdedbebb1dd7b216417b4810f8a07b55f7`다. 문서 내용 기준이며 미커밋 파일을 특정 배포 버전처럼 취급하지 않는다. W08의 사진 업무정보·보수·ROI 수정/복구삭제와 W10의 성능 배너 제거도 행렬에 포함했다.

C05 확정 회신 후 다시 읽은 허브 계약 내용 SHA-256은 `a6f0d3915e5795e21f91fb3742751021748cdb4b731895e4e85a87ea94de054e`다. 같은 랙의 완료된 사진과 새 사진을 별도 보수 항목으로 확인하는 조건을 V3-12·13에 반영했다. 신규 실행은 하지 않았다.

같은 준비 후속에서 C06도 확정 회신을 반영했다. 유효 등급 하향 시 자동대상만 제외하고 업무ID·상태·방법·이력은 보존하며, 재상향은 같은 ID와 명시 수동제외를 유지한다. 수동등록 출처를 자동판정과 구분한다. 계획닫힘 중 receiving은 임시파일/세션 보존·finalize409 후 재개하여 같은 세션으로 완료하고, 이미 completed이면 닫힌 계획에서도 같은 사진을 반환하는 상태 계약을 C02에 기록했다. 모두 구현/실행 미검증이다.
