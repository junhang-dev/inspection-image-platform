### 실제 HTTP·SQL 사례

1. 익명 업무 조회 401, 조회자 읽기 허용·작성 403, 업무담당 계정 관리 403, 관리자 계정 관리 허용, 자기 관리자 권한/사용 상태 낮춤 409, 첫 설정 재호출 409, 잘못된 Origin·누락 CSRF 거부.
2. 업무담당 계획 생성·수정·재조회, 오래된 버전 409, 관리자 필드 혼합 403. 클라이언트 actor 위조에도 이력은 실제 로그인 신원으로 기록.
3. 합성 사진 4장의 실제 청크 전송·완료·재조회. 다른 업무담당의 전송 조회·청크·완료·재시작 거부. 조회자가 읽은 원본 바이트의 SHA256 일치. 반복 완료에도 같은 사진 ID 유지.
4. 사진별 보수 생성·수정·재조회와 버전 충돌, TA 묶음 생성·멤버 버전 충돌·중복 배정 거부, 저장한 멤버의 미배정 목록 제외, 이력의 실제 계정 ID 대조.
5. 표시 이름만 바꾸면 기존 로그인 유지. 역할·활성 상태·관리자 비밀번호 재설정 후 기존 세션 회수. 비활성 로그인 차단.
6. 잘못된 현재 비밀번호 422와 기존 로그인 유지, 본인 비밀번호 변경 후 다른 세션 회수·새 세션 유지, 로그아웃 뒤 업무 API 401.

단일 상위 검사와 5개 하위 검사가 Node 결과의 6개다. 49개 업무 API 전체를 HTTP로 실행한 수치가 아니다.

### 브라우저 확인

- 조회자: 실제 로그인, 계획 만들기·사진 추가·계획 수정 저장·TA 선택/만들기 비활성. 계획 상세와 이력, TA 묶음 조회, 내 계정 사용. 계정 관리 메뉴 없음. 로그아웃 후 업무 화면 닫힘.
- 업무담당: 실제 로그인, 보수 상세 진입, 상태 변경 저장. 상세 GET 502 중에도 저장 완료와 갱신 실패 안내 유지·dirty 해제·다음 PATCH 성공. DB의 실제 상태와 이력 대조.
- TA: 미배정 사진 2장을 골라 실제 묶음 생성. 저장 뒤 보수 쿼리 502에서 작성·선택 잠금 유지. 정상 재조회 후 두 사진이 미배정에서 제외되고 잠금 해제. 실패 안내의 수동 재조회 버튼 클릭은 성공을 확인하지 못했으며 자동 재조회 복구로 판정한다.
- TA 정상 저장: 별도 합성 사진 2장으로 묶음을 만들었다. 저장 후 작성기가 닫히고 `새 작업 묶음` 버튼으로 초점이 돌아왔다. 새로고침 뒤에도 묶음·멤버 2장·미배정 0건이 유지됐고 DB 멤버 수를 대조했다.

## 확인의 한계

- 합성 사진의 등급은 업무 경로 검증을 위한 사람 수정값이다. 실제 모델 추론·성능 증거가 아니다. 새 업로드→AI 판독 완료는 별도 확인이 남아 있다.
- 개인 개발 DB에는 사용자가 만든 관리자 1개가 유지되며 검증 계정은 넣지 않았다. 원본 300장이나 기존 업무 기록을 수정하지 않았다.
- `finishMaintenanceSave`의 목록 실패 검사는 reject하는 callback을 사용한 함수 수준 증거다. 실제 `notify`의 목록 갱신은 revision을 올리고 오류를 목록 상태에 기록하므로, 목록 실패가 모두 보수 창 경고로 전달됐다고 해석하지 않는다. 이번 브라우저 실패 재현은 상세 GET 및 TA 보수 쿼리다.
- 전체 디자인에 대한 사용자 만족, 현업의 권한·업무 규칙 승인, 백업 복구 실행, 운영 인증·SSO·팀별 열람 제한을 대신하지 않는다.

### 개인 개발 서버 재적용 확인

검증한 API 정책·보수 저장 수정·화면 안내를 개발 checkout에 해시 대조 후 반영하고 `4100` API를 재시작했다. 개인 개발 웹 `3100`에서 기존 관리자로 로그인된 상태가 유지됐다. 개발 health는 `200`, `ready=true`, `dataScope=local-private`; 익명 계획 조회는 `401`이다. 인증 계정은 관리자 1개다. 기존 개발 자료 4개 표의 전체 행 수와 직렬화 해시가 반영 전과 일치했다: entities 335, history 420, 묶음 연결 0, 업로드 전송 3. API 재시작 뒤 모델 상태를 확인하거나 새 업무 자료를 저장하지 않았다.

운영 API `4000`은 health `200`, `ready=true`, `dataScope=shared`만 읽었다. 운영 데이터·프로세스·소스는 바꾸지 않았다. 이 확인은 새 인증 코드의 운영 실행이나 배포가 아니다.

## Git과 운영 반영

인증 전 UX 사본, 최초 인증 사본, 이번 검증 후 소스·검사 결과를 각각 보존한다. 공통 `page.tsx`와 CSS에 목적이 겹치므로 파일별로 임의 분리하지 않는다. 개발 후보의 로컬 기록과 운영 반영을 구분한다.

현재 worktree와 개인 checkout은 기준 커밋 `2ec2038282f550791bb70e87090190f091e8d067`에서 시작했다. 검증 코드를 개인 checkout에 반영했지만 index는 비어 있고 stage·commit·push·PR·운영 배포는 실행하지 않았다. 추적 파일 26개가 수정됐고, 인증 파일·검사·문서가 추가됐다. `src/app/page.tsx`에는 UX와 인증·TA 수정이 함께 있다. 이것을 인증 전용 커밋이라고 나눠 부르지 않는다.

1. 현재 후보 전체를 `codex/jun/dev-auth-workflow-20261011` 같은 별도 작업 브랜치에서 리뷰할 수 있게 보존한다. 제안 이름이며 현재 브랜치는 생성하지 않았다.
2. 검증한 개발 후보를 브랜치에 고정하고 원본·DB·가중치·비밀·임시 검증 자료·생성물을 제외한다. `next-env.d.ts`, `inspection-images.zip`, `output/`, `node_modules/`는 검토 후보에 포함하지 않는다.
3. 인증 UI·API·공통 권한 JSON·Docker 패키징·개발 실행 명령은 함께 검토한다. 초기 UX와 이번 저장 복구가 섞이는 부분은 보존한 사본과 비교한다.
4. 운영용 계정 정책 또는 SSO, HTTPS 쿠키, 관리자 인계·복구, 팀별 열람 범위를 정한다. 현재 `AUTH_MODE=local`은 공유 운영에서 시작을 거부한다.
5. 합의한 후보만 main에 정상 통합·push하고, 별도 릴리스 디렉터리에서 배포한다. 진행 중 업로드·판독과 이전 릴리스·DB·객체 보존을 확인한다.
6. 운영 주소에서 로그인·역할별 허용/거부·원본 조회·저장 재조회·로그아웃을 확인한다. 이번 빌드 성공을 운영 배포 성공으로 표시하지 않는다.

현업 보수 조치 규칙과 모델 비교·제품 반영은 별도 후속 작업이다.
