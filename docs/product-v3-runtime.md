# Drone Inspection Platform v3 실행 계약

이 문서는 계획·자동 보수·ROI 구현과 실제 후보 검증의 운영 기준이다. 제출 주소와 최종 배포 버전은 README 및 배포 기록을 따른다. 기존 `docs/uploads.md`, `docs/maintenance.md`의 v2 설명 중 아래와 다른 상태·관계 규칙은 이 문서가 우선한다.

## 업무 상태

- 새 계획은 생산팀 하나와 해당 팀의 랙 1개 이상을 가진다. 팀마다 30개 랙 ID가 있으며 기존 12개 랙의 ID·가상 좌표는 보존한다. 추가 랙의 미확인 지도 좌표는 만들지 않는다.
- 새 사진은 진행 중이며 표시 중인 계획과 랙을 명시한다. 포인트 연결은 선택사항이다. 사진에 계획·팀·랙을 직접 저장하고, 기존 위치 미확인 사진에 위치를 추정해 넣지 않는다.
- 같은 전송 ID의 재시도는 같은 사진을 반환한다. 별도 업로드 차수의 같은 파일은 별도 사진이다. 전송 도중 계획을 완료·취소·삭제하면 최종 저장은 409이며 받은 바이트와 검사 ID는 보존한다. 계획을 복원·재개하면 같은 전송을 완료할 수 있다. 이미 완료된 전송은 닫힌 계획에서도 기존 결과를 반환한다.
- 기존 버전이 수락한 미완료 전송은 서버가 저장한 계약에 따라 재개한다. 새 요청이 이전 계약을 선택할 수 없다.
- 사용 중인 계획 범위를 줄이면 관련 사진·복구 가능한 전송·보수 기록을 확인해 409로 안내한다. 삭제는 숨김이며 복원 시 이전 진행 상태를 유지한다. 사진·원본·후속 판단·이력을 연쇄 삭제하지 않는다.

## 자동 보수와 이력

유효 등급은 사람 수정값이 있으면 그 값, 없으면 실제 전체 사진 AI 등급이다. 유효 3~5등급은 자동 보수 검토 대상이다. 기존 `(planId, pointId)` UUID는 그대로 쓰고, 포인트 없는 사진은 사진 ID별 UUID를 사용한다. 같은 랙이라는 이유로 서로 다른 사진을 한 업무로 합치지 않는다.

`inclusionMode`는 `auto`, `include`, `exclude`다. 자동 포함 여부가 바뀌어도 저장된 작업 상태·방법·TA·ID·이력은 유지한다. 명시한 제외와 숨김은 자동 판정으로 되살리지 않는다. 전체 업무 목록과 TA 필터는 별개다. 업무 사진과 기존 검증 목적 자료를 자동 판정에서 섞지 않는다.

완료된 업무에 새 근거가 생기면 `newEvidenceCount`를 표시한다. 상태나 TA만 저장해도 새 근거를 확인한 것으로 처리하지 않는다. 화면에서 실제 확인한 사진 ID와 판독 fingerprint를 `acknowledgedEvidence`로 명시하고, 서버가 최신 값과 대조한다. ROI 결과는 전체 사진의 유효 등급이나 보수 판정에 대입하지 않는다.

보수 조회는 하나의 메타데이터 스냅샷에서 필터·전체 건수·페이지를 계산한다. 전체 보존 검사에는 `recordPurpose=all&inWorklist=all&visibility=all`을 사용한다. 계획·사진·보수·ROI 수정에는 수정자·사유·읽은 수정 버전이 필요하다.

## 모델과 ROI 서비스

전체 사진 모델은 기존 `MODEL_API_URL`로 연결한다. ROI·설명은 별도 `ROI_API_URL=http://127.0.0.1:8103`으로 연결한다. ROI 서비스를 설정하지 않으면 화면에서 준비 중 상태를 표시하며 전체 사진 판독은 계속 사용할 수 있다. 구현 의존성은 모델 PR #23의 `f63ac733` 및 이후 호환 버전이며 설정·실행 방법은 `ml/ROI_SHAP_API.md`를 따른다.

검증에 사용한 동결 모델 식별자는 다음과 같다.

- 모델: `mobilenetv3small-ft-20260921T074822Z`
- 전처리: `rgb-first-frame-exif-full-resize224-imagenet-v1`
- checkpoint SHA-256: `21245b2f2d8b478b7b2762c51e7882692babd062eb1de8ec305cb090a7906753`

ROI는 EXIF 방향을 적용한 첫 프레임의 정규화 좌표와 원본 SHA·ROI ID·수정 버전에 연결한다. 실제 픽셀 범위는 왼쪽·위쪽을 floor, 오른쪽·아래쪽을 ceil로 계산한다. 서버는 원본 바이트의 크기와 SHA를 확인한 뒤 모델로 전송한다. 고정 test의 source ID나 실제 SHA가 일치하면 새 설명을 계산하지 않는다.

설명은 실제 `shap.GradientExplainer` expected gradients의 signed 224×224 logit 기여도다. 원본·모델·대상 등급·배경·기법·표본 수·seed·ROI 버전이 일치해야 현재 결과로 표시한다. 지도합·scale·잔차식과 절댓값 잔차 허용 범위를 검사하며 정밀도 부족 결과는 정상 설명 완료로 표시하지 않는다. 표시 강도는 색의 진하기만 바꾸고 원래 기여도·등급·품질 판정을 바꾸지 않는다.

DB당 ROI worker는 하나만 실행한다. 계산 중 취소·ROI 변경·사진 숨김을 결과 저장 시 다시 확인한다. 최종 DB 쓰기가 실패해 남은 running 작업은 다음 worker 주기에서 failed로 회수하며 자동 재추론하지 않는다. 재시작 중단 작업도 실패 상태와 다음 행동을 안내한다.

## 실행·전환

기존 `DATA_SCOPE`, 검증된 `DATASET_PLAN_PATH`/SHA, DB·버킷 실행 표식과 자격 범위 검사는 유지한다. 전용 로컬 프로필을 공개 origin으로 연결하지 않는다. 원본 300장의 공개 범위 변경은 해당 데이터와 목적지의 별도 승인 및 명시적 공유 프로필을 필요로 한다.

웹의 `/api` rewrite 대상은 **빌드할 때** `API_INTERNAL_BASE_URL`로 고정한다. 배포 목적지 API에 맞춰 빌드하고 같은 source manifest의 standalone·static·public을 함께 실행한다. 실행 후에 환경변수만 바꾸어 빌드된 대상이 바뀐 것으로 간주하지 않는다. API는 loopback에 두고, 공개 주소의 Origin은 합의한 CORS 목록에 명시한다.

전환 전 최신 DB 원문·전체 이력·업로드 세션·객체 목록 및 원본 해시를 보존한다. 이전 API를 멈춘 뒤 같은 DB를 쓰는 작성 프로세스 하나만 시작한다. DB를 초기화하거나 원본을 삭제해 검사를 맞추지 않는다. 이전 소스·설정과 스냅샷은 복구용으로 남긴다.

## 최종 공유 자료와 공개 응답

2026-09-22 사용자가 원본 사진 300장과 판독·업무 기록의 최종 사이트 공개를 명시적으로 승인했다. 원본의 기존 분리·파일·판독을 수정하지 않고 별도 공유 저장소에 기존 공유 자료와 함께 복제한다. 원본 사진·DB·가중치·비밀정보는 GitHub에 포함하지 않는다.

공유 공개 정책은 승인된 원본 manifest SHA, 사진 300건에 해당하는 고유 이미지 SHA 299개, HTTPS 목적지 origin에 묶인다. 실제 DB 사진의 출처 ID·manifest·바이트 SHA를 검사하며 승인되지 않은 원본이나 출처와 SHA가 다른 행은 시작을 막는다. 기존의 일반 업로드 사진과 승인된 demo 자료는 유지한다.

공유 JSON 응답은 사진·이력·전송·ROI·오류 내부까지 같은 정제를 적용한다. 원본 경로·파일명·학습 및 평가 분리·원본 출처·객체 키·가중치 경로를 외부로 내보내지 않는다. 공개 승인은 고정 test의 새 판독·ROI 추론을 허용하지 않는다. 해당 사진은 저장된 판독과 업무 이력을 계속 볼 수 있다.

최종 저장소 조립 시 기존 공유 사진 80장과 승인 원본 300장, 총 380장을 보존했다. 기본 업무 사진은 357장이고 기존 검증·시연 목적 구분은 유지한다. 사진 고유 객체 379개의 바이트·SHA를 전수 대조했으며 기존 두 저장소의 행·이력은 변경하지 않았다. 조립 후 행은 업무 엔터티 411개·이력 671개·완료 전송 16개·전송 청크 18개다. 이 수치는 사용자 추가 작업 전 조립 시점의 기준이며 외부 배포 검증은 별도 배포 기록을 따른다.
