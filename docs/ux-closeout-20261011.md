# 개발 화면 개선 종료 보고와 운영 반영 계획

**기준일:** 2026-10-11 · **상태:** 사용자 요청으로 개선 목표 중단, 변경 보존

**후속 승인:** 이 보고 이후 개발용 로그인·역할별 권한을 별도 구현했다. [인증 작업 보고](auth-implementation.md)를 따른다. 아래 프론트엔드 중심 변경·웹 단독 배포 검토는 인증 전 UX 사본에만 해당한다. 인증은 API·인증 테이블·권한 JSON을 함께 검토해야 하며 공유 운영에서 아직 활성화할 수 없다.

**후속 실행:** 사용자가 핵심 미완료 항목의 추가 진행을 승인했다. 보수 저장 뒤 상세 조회 실패를 수정하고, 합성 자료의 보수·TA 실제 저장 및 권한 회수를 검증했다. 아래 종료 시점의 미검증 표를 소급 변경하지 않으며 최신 확인은 [권한·저장 검증 보고](auth-verification-20261011.md)를 따른다.

현재 변경은 개발 환경의 개선 후보로 보존한다. 화면 정리와 조회 오류 복구에는 확인된 성과가 있다. 저장 후 동작과 전체 업무 흐름의 확인이 남아 있으므로, 누적 변경 전체를 곧바로 운영에 반영하기는 어렵다. 먼저 별도 브랜치에 보존하고, 검토할 변경 묶음과 첫 운영 후보를 정하는 순서를 권장한다.

## 잘 안 된 부분

1. **작은 수정이 큰 미커밋 묶음으로 쌓였다.** 단계별 확인은 있었지만 검토 가능한 후보를 고정하는 시점이 늦었다. 지금은 화면 배치와 저장 보호 변경이 함께 보여 사용자가 판단하기 어렵다.
2. **목표 종료 조건을 충분히 닫지 못했다.** Done 7개 중 메뉴 항목만 기록 기준 완료이고, 나머지 6개는 부분 확인 상태다. 계속 발견되는 작은 후보를 따라가면서 전체 흐름이 좋아졌는지 평가하는 비중이 낮아졌다.
3. **기록은 많지만 읽기 쉬운 결과 요약이 부족했다.** 기존 체크포인트는 종료 직전 945줄이다. 다음 작업자는 이 종료 보고를 먼저 읽고 필요할 때 상세 기록을 찾아야 한다.
4. **저장 흐름 검증이 부족하다.** 개발의 저장 묶음이 0개이고 임의 업무 자료를 만들지 않는 경계가 있어, 핵심 성공·실패 경로를 확인하지 못했다. 이는 남은 검증 항목이며 사용자 검토 부족을 이유로 완료 처리할 수 없다.
5. **공통 파일의 영향 범위가 크다.** 현재 `page.tsx`는 6,639줄이다. 이번 변경은 계획·사진·보수·TA와 공통 창·메뉴에 걸친다. 파일을 나눠 stage하는 것만으로 독립적인 변경이 되지는 않는다.

## 운영 전에 확인할 동작

| 확인 대상 | 현재 판정 | 첫 운영 후보에서의 처리 |
| --- | --- | --- |
| TA 묶음 저장 성공, 저장 후 미배정 목록 제외·선택 잠금 해제·초점 복귀 | 실제 저장 미검증 | 확인 전 반영 보류 |
| 저장 뒤 조회 실패, 재조회, 동기화 중 다른 탭 이동 | 실제 저장 미검증 | 성공 경로와 함께 검증 |
| 보수 기록 저장 중 이동 잠금, 실패·버전 충돌, 이력 보존 | 정적 확인과 일부 초안 검증 | 실제 개발 저장·재조회로 확인 |
| 쓰기는 성공했지만 뒤이은 보수 기록 GET이 실패한 경우 | 실제 재현 미실행 | 저장 성공 여부 안내와 재시도·버전 충돌 복구 확인 |
| 계획 생성·수정·상태 변경과 조회 실패 시 변경 잠금 | 화면·코드 근거, 누적 변경 전체의 저장 회귀 미확인 | 최초 운영 후보에 포함하려면 저장·이력 재조회 확인 |
| 사진 전송 중 계획 조회 실패, 전송 중단·저장 상태 재확인 | 이번 diff에 복구 동작 변경 포함, 현재 전체 경로 미검증 | 전송 복구 확인 전 해당 변경 보류 |
| 저장된 묶음 상세, 긴 목록, 작성 버튼의 동적 노출 | 현재 자료 부족 | 합의한 개발 검증 자료에서 확인 |
| 새 업로드부터 AI 판독 결과 재조회까지 | 개발 모델 준비 안 됨 | 필요 시 별도 개발 검증. UI 점검을 판독 성공으로 계산하지 않음 |
| 운영용 빌드와 전체 자동 검사 | 이 누적 소스 기준 미실행 | 운영 후보를 고정한 뒤 실행 |

최근 최종 소스의 `npm run typecheck -- --incremental false`와 `git diff --check`는 통과 기록이 있다. 이번 종료 감사는 해당 기록과 현재 파일 상태를 대조했으며 검사 스위트·빌드를 새로 실행하지 않았다. 기존 테스트는 주로 서버 계약을 확인하므로 브라우저 저장·초점·이탈 흐름은 별도 확인이 필요하다.

서버, API 경로, DB 구조, 모델, 의존성·lockfile은 이번 추적 diff에 없다. 프론트엔드가 같은 API를 호출하는 시점과 변경을 잠그는 조건은 달라졌으므로, 서버 변경이 없다는 사실만으로 저장 동작의 안전을 판단할 수 없다.

독립 정적 감사는 보수 편집 화면·묶음 작성기·조회 훅의 지정 범위에서 확인된 차단 버그를 찾지 못했다. 실제 저장 검증을 대신하지 않는다. 별도 문구 검토 항목으로, 묶음 구성원의 `none` 상태를 기존 `상태 미지정`에서 `등록 전`으로 바꾼 부분이 있다. 보수 상태와 보수 대상 등록 여부는 별개이므로 이 표현은 첫 운영 후보 검토에서 의미를 다시 확인해야 한다. 이번 종료에서는 제품 코드를 수정하지 않았다.

## 커밋과 push와 배포의 차이

| 작업 | 바뀌는 것 | 판단 기준 |
| --- | --- | --- |
| 로컬 commit | 코드 변경에 이름과 버전을 붙여 PC의 Git 이력에 저장 | 보관할 소스의 범위와 비밀·자료 제외를 확인 |
| 작업 브랜치 push | 해당 코드를 GitHub 원격 브랜치에 공유 | 공개 가능한 파일인지 확인. 운영 반영과 별도 |
| main 반영 | 제품 기준 이력에 변경을 통합 | 검토·검증된 후보만 정상 통합 |
| 운영 배포 | 실제 사용자가 보는 실행 버전을 전환 | 고정 후보, 사용자 검토, 검증·복구 준비 필요 |

별도 브랜치에 현재 코드 전체를 보관하는 커밋은 가능하다. 그 커밋을 첫 운영 릴리스로 선택할지는 별도로 결정한다. 현재 상태는 한 번에 운영 반영하기보다 단계별 후보를 만드는 편이 적절하다.

## 권장 Git 전략

### 1 현재 변경을 별도 브랜치에 보관

- 제안 브랜치: `codex/jun/ux-checkpoint-20261011`. 아직 생성하지 않았다.
- Git 작성 담당은 한 명으로 고정한다. 현재 detached worktree에 브랜치를 붙이는 방법을 우선 검토하고 개발 checkout의 `main` 변경은 보존한다.
- 원격 상태와 진행 중인 Git 작업을 실행 직전에 다시 확인한다. 변경이 생겼으면 기존 미커밋 상태를 덮지 않고 통합 방법을 정한다.
- 소스와 공개 가능한 README 변경만 경로를 지정해 stage한다. `git add .`로 미추적 파일을 함께 넣지 않는다.
- `next-env.d.ts`는 개발 실행이 만든 `.next/dev/types` 경로 변경이다. 현재 파일은 보존하고 제품 변경 커밋에서는 제외하는 것을 권장한다.
- 원본 zip, `output/`, `node_modules`, 환경·DB·가중치 파일은 제외한다. 상세 체크포인트·API 조사·종료 보고도 공개 가능한 요약과 로컬 기록을 검토한 뒤 분리한다.
- 보관 목적의 커밋 메시지 예: `chore: 개발 화면 개선 후보 보존`. 이는 운영 검증 완료를 뜻하지 않는다.

### 2 검토 단위와 첫 운영 후보를 구분

| 검토 묶음 | 주 내용 | 권장 순서 |
| --- | --- | --- |
| 화면 표시와 진입 | 세 화면의 위계·접기·문구·모바일·행 진입·메뉴·3D 안내 배치 | 첫 운영 후보로 우선 검토 |
| 조회와 복구 | 오류 분리·캐시·건수·재조회·초점 복귀 | 해당 화면과 함께 조건·실패 경로 검증 |
| 초안과 저장 | 보수·TA 초안 이탈, 저장 중 이동 잠금, 저장 후 목록 동기화 | 실제 저장 확인 뒤 후속 후보 |
| 계획과 사진 전송 보호 | 계획 조회 실패 시 생성·수정·전송 잠금과 전송 복구 | 계획 저장·전송 복구 확인 뒤 후보 결정 |
| 설명 문서 | 사용자용 변경 요약, 검증과 남은 제약 | 해당 후보의 코드와 함께 커밋 |

이 표는 검토 분류이며 이미 독립 실행 가능한 커밋이 만들어졌다는 뜻은 아니다. 같은 `page.tsx`·CSS·공통 컴포넌트에 의존하는 변경은 함께 묶어야 한다. 보관 브랜치에서 시작한 뒤, 필요하면 별도 깨끗한 후보 worktree에서 승인할 범위만 재구성한다. 현재 원본 변경은 되돌리거나 덮지 않는다. 분리할 수 없는 부분은 한 후보로 검토하고 저장 검증 전 운영 반영을 보류한다.

예를 들어 `maintenance.ts`의 조회 revision 추적과 `page.tsx`의 저장 후 묶음 소속 확인은 한 변경 단위다. 보수 편집 보호는 `MaintenanceContext.tsx`·`MaintenancePanel.tsx`와 부모의 이탈 처리, 묶음 작성기 UI는 해당 컴포넌트·스타일과 부모의 선택·열기 처리까지 함께 검토한다.

### 3 검토용 브랜치만 정상 push

공개 파일 검토를 마친 뒤 작업 브랜치만 push하고 초안 PR을 만든다. PR에는 화면별 변경, 실제 확인, 저장 미검증, 운영 제외 범위를 먼저 쓴다. 후보와 이력이 고정돼야 비교·되돌리기가 쉽다. main 직접 push·강제 push·기존 이력 수정은 이 보관 전략에 포함하지 않는다.

이번 종료 요청은 전략 수립 범위다. 브랜치 생성·stage·commit·push·PR 생성은 별도 실행 지시 뒤 진행한다.

## 사용자가 검토할 화면

코드 전체를 읽는 대신 아래 4가지 흐름을 짧게 확인하면 첫 운영 후보의 방향을 정할 수 있다. 실제 저장을 필요한 흐름에만 합의한 개발 자료로 추가한다.

1. **검사계획:** 새 계획을 시작할 위치가 보이는지, 기존 계획의 사진·판독과 계획 관리가 쉽게 구분되는지.
2. **보수관리:** 상태별 목록을 고르고 행을 열었을 때 사진·등급·현재 보수 상태가 쉽게 연결되는지.
3. **워크리스트:** 사진별 보수 기록과 여러 사진을 묶는 TA 작업의 차이를 이해할 수 있는지, 선택·해제·작성·이동 확인이 자연스러운지.
4. **공통 흐름:** 뒤로 이동하거나 실패 후 다시 조회해도 조건·초안·현재 위치를 이해할 수 있는지. 업무에서 쓰는 작은 화면 폭도 포함한다.

에이전트는 코드의 회귀와 API 결과를 확인하고, 사용자는 화면의 방향과 현업에 보여줄 수준을 판단한다. 현업의 등급별 조치 규칙과 모델 비교 기준은 별도 과제로 유지한다.

## 운영 반영과 복구 순서

1. **운영 후보를 고정한다.** 사용자 화면 검토와 개발 저장 검증을 마친 범위만 후보 커밋으로 만든다. 타입 검사·기존 자동 검사·운영용 빌드의 실제 결과를 기록한다. 통과·실패·선택적 인프라로 건너뛴 검사를 구분한다.
2. **별도 후보 포트에서 연다.** 빌드 시 API rewrite가 `4100`이 아닌 운영 대상 `4000`으로 만들어졌는지 확인한다. 운영 API에 연결한 후보의 업무 변경은 최종 승인된 확인 범위에서만 한다.
3. **이전 릴리스와 데이터 복구 준비를 확인한다.** 진행 중인 업로드·판독, DB·객체 보존 상태와 이전 웹 릴리스·실행 설정을 확인한다. 운영 자료를 개발 DB에 덮어쓰는 작업은 포함하지 않는다.
4. **최종 반영 승인을 받은 뒤 웹 릴리스를 전환한다.** 현재 변경은 프론트엔드 중심이므로 우선 웹만 전환하는 범위를 검토한다. API·DB·사진 저장소·모델·터널은 기존 배포 절차에 따라 유지한다. 실행 중 개발 폴더를 직접 운영으로 쓰지 않는다.
5. **고정 HTTPS 주소에서 결과를 확인한다.** 3D, 계획 목록, 사진과 기존 판독·이력, 보수 상세와 승인된 저장 경로를 확인한다. 버전·BUILD_ID·데이터 건수를 기록한다. health만으로 업무 성공을 표시하지 않는다.
6. **검증된 커밋을 main에 정상 반영한다.** 기존 [배포 절차](deployment-v3.md)의 후보 검증·운영 전환·기록 순서를 따른다. 리뷰한 커밋과 실제 배포 소스가 같은지 확인하고 원격 main 반영 결과를 기록한다.

조회·상세 진입·저장·필터에 회귀가 발견되면 보존한 이전 웹 릴리스로 돌아간다. 웹만 변경한 경우 DB 전체 복원을 기본 원복 수단으로 사용하지 않는다. 새로 저장된 업무 기록까지 사라질 수 있으므로 데이터 문제는 별도로 진단한다. 코드와 실행 버전의 원복, 데이터 복구를 구분한다.

## 다음 재개 시 기준

- 이번 자율 개선 목표는 중단 상태다. 새 UX 후보 구현을 이어가려면 사용자의 재개 지시가 필요하다.
- 먼저 이 보고와 현재 Git 상태를 확인한다. 이전 체크포인트의 진행 중 표시는 과거 작업 기록으로 읽는다.
- 로그인·역할별 권한은 조사만 했다. 실제 사용자 인증과 역할별 API 제한은 미구현이다. 이번 화면 후보의 완료나 배포 성과에 포함하지 않는다.
- 업무 규칙 자동화와 모델 개선은 별도 트랙이다. 등급을 보수 지시로 확대하거나 새 모델로 교체하지 않는다.
- 자세한 증거는 [개발 화면 체크포인트](ux-workflow-checkpoint.md), [권한 API 조사](authz-api-inventory.md), [기존 운영 절차](deployment-v3.md)에 보존한다.
