# 개발용 로그인과 역할별 권한

**기준일:** 2026-10-11 · **범위:** 개발 `3100/4100`, `local-private`

**후속 검증:** 사용자의 추가 진행 지시에 따라 같은 소스의 합성 검증 환경 `3300/4300`에서 역할별 저장·거부·회수와 실제 브라우저 저장을 확인했다. 상세 결과와 남은 운영 조건은 [권한·저장 검증 보고](auth-verification-20261011.md)에 기록한다. 아래 최초 적용 확인과 후속 실행을 구분한다.

사용자는 자체 계정으로 먼저 구현하고 사내 SSO는 나중에 연결하기로 했다. 역할은 관리자·업무담당·조회자로 정했다. 기존 화면 흐름 자율 개선 목표는 중단 상태로 보존하며, 이 문서는 이후 승인한 별도 인증 작업의 결과다.

## Goal · Boundary · Done

- **Goal:** 로그인한 계정으로 업무를 조회·작성하고, 역할에 맞지 않는 작업을 서버에서 거부한다. 관리자가 계정을 추가·관리한다.
- **Boundary:** 전용 개발 DB의 인증 테이블과 개발 화면·API를 수정한다. 운영 배포·공유 DB 변경·SSO 연동·팀별 자료 접근 정책·기존 원본/이력 수정은 포함하지 않는다. 계정 비밀번호는 사용자가 화면에 직접 입력한다.
- **Done:** 로그인·첫 관리자 설정·계정 관리·서버 역할 검사·화면 제어를 연결하고, 합성 환경에서 실제 역할별 허용/거부·저장·회수를 확인한다. 기존 업무 자료 보존과 운영 적용을 별도로 판정한다.

## 1. 역할

| 기능 | 조회자 | 업무담당 | 관리자 |
| --- | --- | --- | --- |
| 위치·계획·사진·판독·보수·워크리스트·ROI/분석 이력 조회 | 가능 | 가능 | 가능 |
| 계획·포인트 작성/수정, 사진 추가, 판독 수정·재판독 | 제한 | 가능 | 가능 |
| 보수 작성/수정, TA 묶음 생성, ROI 작성·분석·취소 | 제한 | 가능 | 가능 |
| 기록 숨김/복원·목적 관리 | 제한 | 제한 | 가능 |
| 계정 목록·추가·역할·사용 상태·비밀번호 재설정 | 제한 | 제한 | 가능 |
| 본인 비밀번호 변경·로그아웃 | 가능 | 가능 | 가능 |

현재 세 역할은 **같은 팀·랙의 전체 자료를 조회**한다. 팀별 열람 제한은 구현하지 않았다. 역할은 화면 작업과 API 권한을 통제하며, 모델 성능이나 현업 보수 조치 기준을 바꾸지 않는다. 새 계정의 기본 역할은 조회자다. 기존 화면에 없는 기록 목적 편집 기능을 새로 추가하지 않았다.

## 2. 사용 방법

1. 전용 설정·DB·MinIO를 준비한 뒤 `npm run dev:private`로 실행한다. 이 명령의 개발 API에는 `AUTH_MODE=local`이 적용된다.
2. `http://127.0.0.1:3100/`에서 처음 한 번 관리자 계정을 설정한다. 아이디는 영문·숫자·점·밑줄·하이픈 3~40자, 표시 이름은 1~40자, 비밀번호는 12~128자다. 아이디는 소문자로 저장하며 비밀번호의 공백을 임의로 제거하지 않는다.
3. 로그인 뒤 상단 **이름·역할** 버튼을 누른다. 관리자는 **계정 관리 → 계정 추가**에서 역할과 계정을 설정한다.
4. 계정의 사용 상태를 끄면 로그인을 막는다. 역할·사용 상태·비밀번호가 바뀌면 그 계정의 기존 세션을 회수한다. 표시 이름만 바꾸면 세션을 유지한다.
5. 본인의 관리자 역할·사용 상태는 낮출 수 없다. 마지막 활성 관리자도 제거할 수 없다. 계정·비밀번호를 채팅이나 Git에 기록하지 않는다.

2026-10-11 사용자가 첫 관리자 설정을 직접 완료했다. 에이전트가 임시 관리자나 기본 비밀번호를 만들지 않았다. 현재 개발 DB에서 관리자 1개를 확인했다. 업무담당·조회자 계정은 아직 만들지 않았다.

## 3. 서버에서 통제하는 부분

- `AUTH_MODE` 기본값은 `disabled`다. `local`은 `local-private`에서만 활성화할 수 있다. 공유 운영에서 `local`을 지정하면 시작을 거부한다.
- 비밀번호는 무작위 salt와 Node.js `scrypt`로 해시한다. 세션 토큰은 32바이트 난수이며 DB에는 SHA256 해시만 저장한다. 쿠키는 개발 포트별 이름·HttpOnly·SameSite Strict를 사용한다. HTTP 쿠키는 전용 loopback 개발에 한정하며 운영 HTTPS 인증은 별도 작업이다.
- 세션은 8시간 절대 만료다. 매 요청에서 현재 역할·활성 상태·세션 버전을 확인한다. 로그아웃은 서버 세션도 제거한다.
- 로그인·첫 설정은 허용 Origin과 JSON을 요구한다. 인증한 변경 요청은 Origin과 세션의 CSRF 토큰을 함께 검사한다. 토큰은 클라이언트 메모리에만 두며 브라우저 저장소에는 넣지 않는다.
- 기존 49개 업무 API의 메서드와 전체 경로를 명시한다. HEAD는 GET 권한을 따르고, 분류하지 않은 API는 거부한다. 로그인한 업무담당이 관리자 필드를 섞어 보내도 서버가 전체 변경을 거부한다.
- 익명 health에는 준비 여부와 개발 데이터 범위만 반환한다. 업무 목록·원본 사진·판독·이력·업로드 전송 정보는 로그인이 필요하다.
- 요청 중 생성되는 업무 이력에는 서버가 확인한 표시 이름·계정 ID·아이디를 기록한다. 과거 actor를 계정에 소급 연결하지 않으며, 백그라운드 AI·복구 작업의 기존 서비스 actor를 유지한다.
- 계정 생성·변경·비밀번호 변경·로그인은 별도 인증 감사 테이블에 기록한다. 계정 수정에는 이름·역할·활성 상태 전후 값을 기록하며 비밀번호·해시는 넣지 않는다.

인증 전용 테이블은 `auth_state`, `auth_users`, `auth_sessions`, `auth_audit`다. 첫 관리자 생성과 계정 변경은 같은 상태 행을 잠가 동시 요청을 직렬화한다. 로그인 해시는 동시 3개로 제한한다. 로그인 시도 제한은 계정별 15분 12회·프로세스 전체 120회이며, 메모리 제한이므로 개발 API를 재시작하면 초기화된다. 운영용 공유 제한 저장소·비밀번호 복구·MFA는 구현하지 않았다.

보안 기준 참고: [OWASP 비밀번호 저장](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [Node.js crypto](https://nodejs.org/api/crypto.html), [OWASP CSRF 방어](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

## 4. 업로드와 화면

- 신규 전송의 소유자를 서버 로그인 계정으로 기록한다. 일반 계정은 자기 전송만 확인·완료·재시작할 수 있다. 관리자만 다른 계정과 소유자가 없는 기존 전송을 관리할 수 있다.
- 기존 전송의 소유자를 다시 초기화하거나 임의로 덮지 않는다. 상태 조회·청크 수신·원본 저장·재시작 파일 삭제·multipart 복사 전에 소유권을 확인한다.
- 브라우저 업로드 큐는 계정별 저장 키를 사용한다. 예전 큐는 보존하며 새 계정에 자동 귀속시키지 않는다. 계정이 바뀌면 진행 중 전송을 중단하고 늦은 상태 저장을 막는다.
- 로그인 상태를 확인하기 전에는 업무 화면을 열지 않는다. 인증 조회 실패는 재조회로 복구한다. 사용자가 바뀌면 기존 화면·큐 상태를 새로 만든다.
- 조회자는 목록·조건·상세·사진 이동·이력을 사용한다. 작성/수정 버튼과 handler는 권한을 확인한다. 서버 검사는 화면 제어와 별개로 유지한다.
- 표시 이름 변경·본인 비밀번호 변경 시 같은 사용자 화면을 유지한다. 오래된 요청의 401은 다른 세션의 로그인 상태를 지우지 않도록 요청 당시 사용자와 CSRF 토큰을 대조한다.

권한 정책은 `src/lib/auth-policy.json`을 서버·웹이 공유한다. API Docker 이미지에도 이 파일을 포함했다. 기존 엄격한 생성 schema에 actor 필드를 추가하지 않고 요청 context로 감사 신원을 전달한다.

## 6. 다음 검토와 Git·운영 전략

1. 합성 검증 환경에서 역할별 허용/거부, 보수·TA 저장, 기존 세션 회수, 비밀번호 재설정·변경, 첫 설정 재호출, 전송 소유권을 확인했다. 사용자가 실제 사용할 업무담당·조회자 계정은 관리자 화면에서 직접 추가한다. 실제 팀·담당 정책의 적합성은 이 합성 검증으로 확정하지 않는다.
2. 기존 UX 미커밋 변경과 인증 변경을 별도 목적의 후보로 보존한다. 공통 `page.tsx`에는 두 목적이 겹치므로 파일 전체를 인증만의 변경이라고 stage하면 안 된다. 인증 시작 전 UX 사본과 비교한 별도 diff로 검토한다.
3. 로그인 UI·API·공통 권한 JSON·이미지 패키징·실행 명령을 같은 변경 단위로 묶는다. 테스트가 필요한 경우 사용자 확인 범위에 맞춰 추가하며, DB·비밀번호·세션·원본·출력물을 커밋하지 않는다.
4. 현재 자체 계정은 공유 운영에서 활성화할 수 없다. 운영 적용 전 SSO 또는 운영용 계정 정책, HTTPS 쿠키, 관리자 인계·복구, 팀별 열람 정책과 배포 검증을 별도로 정한다. 인증 후보는 이전 UX 웹 단독 배포 절차에 포함하지 않는다.
5. 이번 작업은 개발 적용까지다. Git stage·commit·push·PR·운영 배포는 실행하지 않았다. 기존 [UX 종료 보고](ux-closeout-20261011.md)의 보관/검토 전략을 유지한다.
