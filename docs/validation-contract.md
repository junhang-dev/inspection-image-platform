# 독립 검증 계약

2026-09-21 최신 사용자 목표를 기준으로 하는 검증 절차다. 실제 실행 결과와 남은 항목은 `records/validation-runtime-2026-09-21.md`에 기록한다. 이 계약 문서 자체는 합격 결과가 아니다. **PlantPilot v2의 새 기준은 11절에 별도 추가하며 전 항목 미실행으로 시작한다.** 기존 버전의 합격 기록은 새 화면·데이터 흐름의 합격을 대신하지 않는다.

## 1. 적용 범위와 우선순위

1~10절은 기존 제품 검증의 추적 기준이다. 새 v2 동작에서 겹치거나 달라지는 조건은 11절과 확정된 `docs/product-v2.md`를 우선하며, 과거 합격 기록을 새 요구의 합격으로 옮기지 않는다.

최신 사용자 목표는 기존 `docs/goal.md`에 더해 사용자 입력에 따른 **dummy 3D 위치 연결**, **보수 검토·진행·완료와 사유**, **검사 캘린더에서 TA 워크리스트까지의 흐름**, 처리시간 목표를 포함한다. 이후 사용자가 실측 두께 자료 이야기를 제외하도록 결정했으므로 실측 자료·두께 예측·실측 누락 오류·관련 질문은 이번 범위에서 제외한다. 실제 좌표 복원·드론 제어가 구현됐다는 뜻은 아니다. Label Studio와 제품 내 재학습은 가능하면 구현하는 항목으로 별도 상태를 보고한다.

판정 결과는 다음 세 영역으로 나눈다. `완료 / 미달 / 미검증`을 사용하고 실행 증거를 연결한다.

| 영역 | 완료에 필요한 증거 | 대체할 수 없는 것 |
|---|---|---|
| 제품 기능 | 아래 흐름·오류·이력·재시작 검사를 실제 실행 | 문서 작성, 빌드 성공만으로 기능 완료 |
| 부식 분류 성능 | 고정한 모델·전처리로 train 정확도 90% 이상, 최종 test 정확도 70% 이상이라는 사용자 합격선 평가 | 파일명 정답 반환, demo 결과, train 정확도만으로 전체 성능 판정 |
| 사용성 확인 | AI의 직접 화면 조작·백엔드 증거로 대표 전체 흐름을 확인하고 발견한 막힘을 수정·재확인 | 자동 조작 시간을 실제 사람의 입력 속도로 표현 |

## 3. 실행 전 고정할 조건

- 제품 커밋, 모델 버전·가중치 해시·전처리 버전, 브라우저 버전, 실행 방식, 기기와 연결 경로를 기록한다. 비밀·원본 경로·원본 이름·전체 manifest·가중치는 공개 기록에 넣지 않는다.
- 기능·시간 검사는 고정 test를 사용하지 않는다. 승인된 demo 5장을 두 번 선택해 10개 업로드 항목을 만들 수 있으나, 동일 파일 중복임을 기록하고 모델 평가나 학습 표본 수로 합산하지 않는다. 중복 업로드를 막는 제품이면 승인된 입력 안에서 반복 표본·재사용 정책을 구분한다. 이 제한을 피하려고 미승인 train 원본으로 검증 범위를 넓히지 않는다.
- 입력 10개의 총 바이트·파일 형식·해상도 범위를 로컬 증거에 남긴다. 10장이라는 개수만으로 모든 파일 크기의 성능을 보장하지 않는다.
- UI 기능 검사는 전용 검증 데이터로 수행한다. 공유 서비스 재시작·오류 주입은 실행 담당과 시간을 조율한다.

## 4. 업무 흐름 체크리스트

각 항목의 실행 여부는 별도 결과 기록으로 관리한다. 결과에는 항목 ID, 실제 행동, 예상값·실제값, 화면/로그, 버전, 상태를 남긴다. 절차가 적혀 있다는 이유로 완료로 표시하지 않는다.

| ID | 실제 조작 | 통과 조건 |
|---|---|---|
| F01 | 빈 상태에서 캘린더로 검사 계획 작성·저장·다시 열기 | 대상·일정이 보존되고 계획과 포인트를 연결할 수 있다. |
| F02 | 사진 10개 업로드, 처리 완료 후 각 사진 재조회 | 모든 접수 항목의 성공·실패가 구분되고 원본/대상/포인트가 다시 조회된다. 중복 정책이 명시된다. |
| F03 | 설비번호·랙 입력 후 dummy 3D에서 선택 | 같은 포인트로 사진/목록/상세가 연결된다. 입력값이 보존되고 화면이 모의 배치임을 표시한다. 실제 지리 좌표로 내보내지 않는다. |
| F04 | 위치 미입력 사진 업로드, 나중에 위치 지정·수정 | 미확인으로 보존된다. 파일명이나 모의 좌표가 실제 위치를 자동 확정하지 않는다. 위치 변경 이력을 볼 수 있다. |
| F05 | 실제 모델의 비동기 처리 중 캘린더·목록·상세 이용 | 대기/처리 중/성공/실패를 구분하고 다른 업무가 계속 가능하다. 모델 미연결을 실제 AI 성공으로 표시하지 않는다. |
| F06 | AI 결과 그대로 사용, 다른 항목은 등급 수정·재조회 | 미검수 결과도 조회·활용 가능하다. 원래 AI 등급과 사람 수정값·사유·수정자·시각이 별도 보존된다. |
| F07 | 재촬영 지정·사유 입력·목록 조회·해제 | 지정/해제와 사유 이력이 보존된다. 실제 요청 전송 여부와 단순 표시를 구분한다. |
| F08 | 관리 워크리스트와 학습 라벨링 후보 각각 지정·해제 | 각 목록과 상세가 일치하며 두 상태가 독립적이다. 후보 지정이 학습 완료로 표시되지 않는다. |
| F09 | 포인트 보수 검토 → 진행 → 완료 변경, 사유 입력·재조회 | 상태마다 수정자·시각·사유·전후 값이 남고 AI 원본은 변하지 않는다. 완료는 사용자의 업무 기록임을 알 수 있다. |
| F10 | 검사 계획 → 사진/판독 → 관리 대상 → TA 반영 | 같은 포인트를 추적할 수 있고 캘린더·워크리스트·상세의 상태가 일치한다. 실제 외부 업무 시스템 반영과 내부 기록을 구분한다. |
| F11 | 대시보드 집계·최근 사진 → 전체 필터 목록 → 사진 상세·이력 조회 | 같은 입력과 필터 조건에서 집계·목록·상세가 일치한다. 원래 AI와 사람 수정값을 구분하고 누락/실패를 정상 완료로 표시하지 않는다. |
| F12 | 새로고침, 서비스 정상 재시작 후 F02~F11 자료 재조회 | 사진, 연결, 원본 AI, 사람 수정, 후속 상태, 계획, 변경 이력이 보존된다. 저장소 볼륨 삭제로 검사하지 않는다. |
| F13 | 같은 수정 동작을 빠르게 두 번 수행, 처리 중 재접속 | 중복 저장/중복 이력이 생기는지 확인하고 정책을 기록한다. 재접속 후 실제 서버 처리 상태를 확인할 수 있다. |

F11/P04는 사용자 원문의 “파인딩사항 레포팅이나 대시보드에서 확인”에 대응하는 **대시보드·목록·상세 조회 경로**를 검증한다. 별도 보고서 파일·인쇄·내보내기 형식은 요구되거나 검증된 것으로 표시하지 않는다.

집계 대조에는 같은 시점의 동일 사진 응답을 사용한다. 전체 수는 저장 사진 수, 시각적 3~5등급 수는 사람 수정값이 있으면 그 값을 우선하고 없으면 원래 AI 등급을 적용한 수, 대기·진행 수는 해당 처리 상태의 수, 재촬영 수는 재촬영 표시가 있는 수다. 최근 사진 5개는 전체 집계의 일부이며 전체 목록과 혼동하지 않는다. 필터 목록은 같은 검색·상태 조건으로 비교하고, 상세의 원본·AI·사람 수정·이력은 같은 사진 ID로 대조한다. 이 시각적 집계는 실제 보수 지시나 모델 정확도 판정이 아니다.

## 6. 시간·응답성 측정

측정은 브라우저 사용자가 인지하는 시작과 종료를 기준으로 하며 API 지연은 보조 자료다. 각 시도별 성공/실패, 경과시간, cold/warm, 동시에 실행한 작업을 기록한다. 최신 합의의 대표 전체 업무 흐름은 1회 계측하며 이미 통과한 검사를 반복하지 않는다. 실패한 시도는 제외하지 않고 새 결함의 수정 후 해당 경로만 재확인한다. 자동 조작 1회는 통계적 성능 보장이나 실제 사람의 속도 측정이 아니다.

| ID | 목표 | 타이머 시작 → 종료 |
|---|---|---|
| P01 | 검사 계획 30초 이내 | 계획 작성 시작 클릭 → 필수 입력·저장 완료와 캘린더 재표시. 입력 문안은 미리 정하되 사용자 입력 시간 포함. |
| P02 | 10장 업로드 30초 이내 | 파일 10개 선택을 마치고 업로드 동작 → 10개 모두 저장/접수 결과 확인. 업로드 중 바이트 전송과 원본 저장 포함, 추론 대기는 분리. |
| P03 | 10장 실제 추론 180초 이내 | 10개 업로드 접수 완료 → 10개 실제 추론 결과가 UI에 표시. 큐 대기 포함; worker cold start는 별도 표기. 1개라도 실패하면 속도 통과만으로 전체 성공 처리하지 않음. |
| P04 | 대시보드·결과 조회 수초 이내 | 대시보드/목록 필터/상세 조회 동작 → 해당 결과 렌더링과 조작 가능. **수초의 정확한 상한은 미합의**이므로 실제 시간을 보고하며 임의 합격선을 확정하지 않음. |
| P05 | 비동기 작업 중 사용성 유지 | P03 동안 P01과 목록·포인트·필터 조작 |
| P06 | 대표 전체 업무 조작 약 1분, AI 판독 대기 별도 | 파일 선택·포인트 입력 시작 → 실제 업로드 → 같은 사진 결과 확인·필요한 수정 → 후속 상태·계획 저장 → 같은 ID의 이력 재조회. AI만 기다린 구간을 명시해 총 경과시간에서 차감. |

P05는 동일 조작을 추론이 없을 때와 있을 때 각각 측정하고 화면 멈춤·중복 제출·결과 깜박임을 기록한다. 단순 백엔드 비동기 응답만으로 사용성 통과로 판단하지 않는다. 기존 P01은 계획 작성 30초로 유지하며 새 대표 전체 흐름을 P06으로 구분한다.

전체 흐름의 “1분 내외”는 **AI 판독 대기를 제외한 업무 조작 시간**으로 사용자 합의가 확정됐다. 총 경과시간, AI만 기다린 구간, 차감 후 업무 시간을 모두 보고한다. AI 처리와 다른 조작이 겹치면 그 조작 시간은 빼지 않으며 업로드·일반 저장·조회 대기는 업무 시간에 포함한다. 시작 전에 파일과 입력 문안을 정할 수 있으나 실제 파일 선택과 필수 입력은 계측에 포함한다. 모든 선택 작업을 반복 지정·해제하는 스트레스 검사를 대표 업무로 대체하지 않는다. 화면·같은 ID의 백엔드 상태·원본 파일 증거를 함께 남기며 AI 자동 조작 시간과 사람 실측을 구분한다.

실제 사용자·동료가 당장 없으면 AI가 직접 검증하고 개선을 계속한다. 사람 사용성 검수는 선택 피드백이며 기능 완료를 막는 관문이 아니다.

## 7. 분류 평가 계약

- 기존 train 231 / validation 58 / 고정 test 10 분리를 유지한다. 원본 중복 제외와 demo 복제본 비집계 규칙을 보존한다. 이 문서 작성에서는 분리 manifest를 재생성·수정하거나 test 이미지를 열지 않았다.
- 최신 사용자 합격선은 **train 정확도 90% 이상, 고정 test 정확도 70% 이상**이다. 고정 test 10장에서는 7장 이상 정답이어야 한다. 이전에 제안된 recall 등의 보조지표는 합격선이 아니다. 합의 시각과 최종 모델·전처리 버전을 기록하고 test로 튜닝하지 않는다.
- 최종 test 10장의 사진별 정답·실제 예측, 정확도(맞힌 수/10)를 로컬 기록에 남긴다. 보조로 5등급 혼동행렬과 1·2 대 3·4·5의 이진 분류 결과를 보고할 수 있으나 별도 승인 없이 새 합격선으로 삼지 않는다.
- 10장 평가의 정확도는 한 장마다 10%p 변한다. 이를 현장 전체 포인트의 성능 보장으로 확대하지 않는다.
- 추론 경로에 정답 라벨·파일명 규칙이 들어가지 않는지 코드 검토하고, 동일 이미지 bytes를 다른 중립 이름으로 추론했을 때 결과가 같은지 검사한다. **최종 평가한 모델·전처리 버전과 제품에서 실제 추론한 모델·전처리 버전의 동일성 증거**를 남긴다. 평가 기록, 실제 로드된 가중치 해시·전처리 설정, 제품 응답의 버전을 대조하며 버전 문자열만 같다는 이유로 동일하다고 판정하지 않는다.
- 10회 이상 개선 시도에도 개선되지 않으면 최신 목표에 따라 연결 가능한 모델과 한계를 인계할 수 있다. 이것은 성능 합격선 면제나 test 재튜닝 허용이 아니다. 시도 수·validation 결과·선택 근거·미달 여부를 기록한다.

## 8. 최신 범위 변경

초기 위임에 따라 과제 관련 자료의 존재 여부를 읽기 전용으로 조사했으나, 이후 허브가 전달한 사용자 결정 “실측 두께 자료 이야기는 빼둬”를 적용했다. 실측 두께 자료·두께 예측·실측 누락 오류·관련 질문은 이번 완료 기준과 후속 질문에서 제외한다. 조사 사실은 행사 이력에만 남긴다.

현재 검증은 사진상 부식 형상 AI와 설비·랙 dummy 3D, 검사 계획·TA 워크리스트, 보수 업무 상태·이력에 집중한다. 시각 등급을 실제 두께나 안전성 판정으로 확대하지 않는 기존 경계는 유지한다.

## 9. 용어·디자인·사용자 검수

- 내비게이션, 제목, 버튼, 토글 설명, 대시보드, 목록, 상세에서 `검사 계획`, `검사 포인트`, `재촬영`, `관리 워크리스트`, `학습 라벨링 후보`, `보수 상태`, `TA 워크리스트`의 뜻이 일치하는지 확인한다.
- `AI 판독`과 `사람 수정`, `시각적 분류`와 `보수 상태`, `미확인`과 `실패`, `dummy 3D`와 실제 위치를 색상만으로 구분하지 않는다. 등급 숫자·텍스트·출처를 함께 확인한다.
- 로딩/빈 상태/오류/저장 성공, 버튼 우선순위, 토글의 현재값과 변경 후 의미, 날짜·시간대·단위 표기, 모바일/데스크톱 주요 화면의 일관성을 실제 렌더링에서 확인한다.
- AI가 대표 전체 흐름을 실제 화면에서 수행하고 백엔드·파일 증거로 대조한다. 실제 결함은 수정 후 해당 경로를 재확인한다. 비개발자 팀원의 수행·도움 요청·오해·시간은 가능할 때 선택 피드백으로 기록하며, 그 대기로 기능 완료나 개선 루프를 중단하지 않는다. 자동화 결과를 사람 검수 완료로 표현하지 않는다.

## 10. 인계할 증거

최신 사용자 완료 기준에 따라 로그의 PASS 표시만으로 업로드·저장을 검증하지 않는다. 공개 demo 사진을 실제 업로드하고 다음 증거를 함께 남긴다.

1. 원본 demo의 파일 크기·SHA-256과 업로드 응답의 사진 UUID, `objectKey` 또는 object ID, `pointId`를 로컬 증거에 기록한다.
2. 백엔드 이미지 조회 API에서 실제 응답 바이트를 다시 받아 원본 SHA-256과 비교한다. 가능하면 MinIO 저장 객체도 읽기 전용으로 직접 조회해 3자 일치를 확인한다. 확인하지 못한 계층은 별도로 미검증으로 표시한다.
3. 브라우저에서 업로드 후 갤러리/목록, 원본이 표시된 상세, 수정 후 다시 연 이력 화면을 스크린샷으로 보존한다. 이미지 요청 성공과 실제 이미지 렌더링도 확인한다.
4. 스크린샷과 API 증거가 같은 사진 UUID·포인트를 가리키는지 연결한다. 공개 demo만 사용하고 비밀·회사 원본·무관한 브라우저 내용은 포함하지 않는다.

검증 기록은 `records/validation-*.md`를 사용한다. 민감한 파일명·원자료 식별자·화면·내부 접속 경로는 Git 제외 `records/validation-*.local.md`에만 남기고 공개 기록에는 승인된 demo와 요약만 포함한다. 비밀은 로컬 기록에도 복사하지 않는다.

각 실행 기록에 시각, 커밋/모델/전처리, 데이터 종류·개수, 실행 방법, ID별 기대/실제 결과, 실패·수정·재검증을 남긴다. 아직 실행하지 않은 칸은 미실행으로 유지한다. 제출 직전 세 영역 상태와 미합의 기준을 확인하고 화면·검증 기록·실제 서비스의 차이를 명시한다.


## 11. PlantPilot v2 검증 계약

허브가 전달한 신규 제품 요구를 검증 가능한 조건으로 정리한 계약이다. 최초 작성 시 전부 미실행이었으며 2026-09-21 첫 구현 단위와 후속 업로드 후보의 검증 결과를 아래에 반영했다. 2026-09-21 작성된 `docs/product-v2.md`의 R01~R15·D01~D11과 문서 대조를 마쳤다. 이 문서 대조 자체는 범위 일치 확인이며 구현·실행 합격을 뜻하지 않는다. 설계가 달라지면 최신 사용자 합의를 우선한다. 아래 상태는 기록된 후보 실행 범위를 기준으로 하며 실제 결과는 별도 버전·증거와 함께 보존한다. 기존 F/P 항목은 이전 제품의 추적 번호로 보존한다.

### 입력·실행 경계

- 원본 300장의 공개·사용 범위는 아직 추가 승인되지 않았다. 승인 사진 또는 제품 설계 D02가 허용한 회사 자료와 무관한 합성 입력만 검증에 사용하고 기존 train/validation/test 분리·원본·실제 모델을 보존한다. 고정 test를 재추론하거나 학습·성능 평가에 demo 복제본을 새 표본으로 세지 않는다.
- 새 커밋·웹 빌드·API·모델 입력 계약을 고정한 격리 환경에서 먼저 실행한다. 공개 사이트에 검증 데이터를 임의로 추가하거나 기존 업무 자료를 삭제하지 않는다. UI의 실험 자료 분리는 원본이나 실험 증거의 물리 삭제를 뜻하지 않는다.
- 가상 정유 1~4팀과 실제 조직·위치는 구분한다. 첨부 지도 자산의 사용 범위·팀 배치 기준은 설계 확정 전 추정하지 않는다. 모델 등급은 여전히 시각적 분류이며 안전·잔여 두께 판정이 아니다.
- 12개 이상 입력과 큰 파일 검사는 업무 입력 수·실제 바이트·형식·해상도·생성/복제 방식을 기록한다. 승인 사진의 복제 또는 회사와 무관한 합성 입력의 생성 근거를 남기고, 새 회사 원본을 가져와 수량·용량 조건을 채우지 않는다.

### v2 증거·판정 방법

각 항목은 실제 화면, 요청·응답, 백엔드 ID 관계, 파일 실체 중 해당 조건에 필요한 증거를 함께 확보한다. `planId` 분리·삭제 복원·워크리스트·자료 목적 변경은 전후 데이터와 이력으로 비교한다. 테스트 데이터의 표시·숨김과 실제 제품의 새 기능 완료를 혼동하지 않는다. 새 수정 화면에 기존 동시 수정 보호가 적용되는지도 변경된 경로에서 확인하며, 이미 통과한 이전 버전의 검사 전체를 기계적으로 반복하지 않는다.

12개 이상 또는 큰 파일 한 개 성공은 모든 수량·용량이 무제한으로 처리됨을 증명하지 않는다. 검증한 입력·동시 전송 수·청크 크기·시간·실패 지점을 기록한다. 사용자에게 보이는 고정 개수·용량 제한 해제와 실제 전송·추론의 자원 경계/오류 처리를 분리해 보고한다. 큰 입력이나 부분 실패 조건을 충족하지 못하면 작은 파일 성공으로 대체하지 않는다.

V2-14는 실제 파일 선택과 필수 입력부터 포함하며, AI 결과만 기다린 구간의 시작·종료를 같은 시계로 남긴다. AI와 겹친 계획·목록 조작, 일반 업로드·저장·조회 대기는 업무 시간에서 빼지 않는다. 삭제 복원·충돌 재시도·모든 상태의 왕복 토글을 한꺼번에 넣은 스트레스 검사는 대표 흐름과 별도로 측정한다. 12개 이상·대용량의 기능 검사는 별도 사례로 두고, 대표 흐름의 입력 개수·바이트를 사전에 명시한다. 자동 조작 시간은 실제 사람의 판단 속도나 현장 효과의 보장이 아니다.

기존 P02/P03의 10장·30초/180초는 성능 표본으로 유지하며 업로드 수량 제한으로 적용하지 않는다. 12개 이상·대용량의 시간은 해당 입력 수·바이트와 함께 별도로 보고한다.

설계·UI·API·모델 입력 계약이 실행 가능한 버전으로 준비되면 각 항목을 `완료 / 미달 / 미검증`으로 판정한다. 실패와 미실행은 그대로 남기고 실제 결함을 수정한 뒤 해당 경로를 재검증한다. 현재 실행 결과는 [첫 구현 단위 독립 QA](../records/validation-v2-first-unit-2026-09-21.md)와 [업로드·가독성 후보 독립 QA](../records/validation-v2-upload-2026-09-21.md)에 기록했다. 표의 부분 확인 범위를 넘는 기능·성능은 미실행이며 모델 최종 test의 기존 미달 결과를 새 기능 검증으로 바꾸지 않는다.
