# 데이터 저장 구조

사용자가 제공한 아키텍처와 현재 합의한 방향입니다. 이 문서는 MinIO·MySQL이 이미 실행된다는 뜻은 아닙니다.

| 저장 위치 | 담는 내용 | 현재 범위 |
|---|---|---|
| Git / GitHub | 코드, Compose 등 설정, 공유 가능한 문서 | 공개 가능한 내용만 검토하여 기록 |
| 로컬 Docker Compose의 MinIO | 사진 원본, 학습 데이터, 모델 파일 | 이번 개발의 파일 저장소 방향 |
| 로컬 MySQL | 이미지 정보, 판독 결과, 검수·변경 이력 | 제품 데이터의 저장 방향 |
| AWS S3 | 향후 서비스 운영의 객체 저장소 | 이번 랄프톤 밖의 확장 |

## 이번에 지킬 계약

- 사진은 Git에 올리지 않습니다. 회사 원본과 기존 학습 목록은 로컬 전용으로 유지합니다.
- MinIO에 저장할 객체와 원본 폴더를 구분합니다. 원본은 이동·개명·삭제하지 않으며 기존 300장을 Git 준비 과정에서 대량 적재하지 않습니다.
- MinIO·MySQL 저장 공간은 Docker 영속 볼륨을 사용하는 방향으로 설계합니다. 컨테이너 교체 후 보존 여부를 확인하기 전에는 영속성을 검증했다고 하지 않습니다.
- bind mount를 사용한다면 `minio-data/`, `mysql-data/`, `volumes/`처럼 명시적인 로컬 제외 경로를 사용합니다. 실제 파일은 Git 기록에 들어가지 않습니다.
- `.dockerignore`도 유지해 Docker 빌드 컨텍스트로 사진·비밀·실행 데이터를 전달하지 않습니다. 실제 빌드 검사는 제품 환경 준비 시 수행합니다.
- 저장소 연결 값과 비밀은 실행 환경에서 주입합니다. 공개 예제에는 가짜 값과 변수 이름만 둡니다.

## 향후 S3 전환을 고려한 구현 방향

애플리케이션의 저장 기능은 S3 API를 사용하는 한곳에 모읍니다. 이미지 정보에는 특정 장비의 절대 경로나 임시 다운로드 URL 대신 `bucket`과 `object_key`를 참조하도록 설계합니다. 외부 주소는 필요할 때 생성합니다.

엔드포인트·리전·버킷·인증 값·주소 지정 방식을 코드와 분리합니다. MinIO에서 AWS S3로 바꿀 때는 설정뿐 아니라 실제 객체 이관, 접근 권한, 업로드·조회·다운로드 주소의 동작도 검증합니다. 엔드포인트 변경만으로 기존 데이터가 이전되거나 모든 기능이 호환된다고 보장하지 않습니다. [AWS의 S3 클라이언트 설정](https://docs.aws.amazon.com/cli/latest/topic/s3-config.html)

장점은 코드 이력을 가볍게 유지하고 파일 저장소의 변경 영향을 줄이는 것입니다. 대신 데이터·볼륨의 별도 보관과 복구 검증이 필요합니다. S3 전환의 비용·외부 전송·배포는 이번 개발 범위에 포함하지 않습니다.

## 제품 담당의 확인 항목

작은 합성 파일로 업로드 → 객체 조회 → 제품 정보 연결 → 컨테이너 재시작 후 재조회까지 확인하고 기록합니다. 회사 사진을 쓰는 로컬 업로드는 기존 사용 범위와 원본 보존 조건을 유지합니다. 서비스의 공개 데모에는 별도 검토한 예제 자료를 사용합니다.

실제 Compose 파일, 기동, 업로드, 재시작 보존, S3 전환 검사는 아직 미실시입니다. 제품 내부 재학습 기능은 이번 필수 흐름에 추가하지 않습니다.
