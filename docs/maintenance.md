# 계획·포인트별 보수 기록

사진의 시각적 등급과 보수 업무 판단을 구분한다. 같은 포인트라도 검사 계획이 다르면 별도 보수 기록을 사용한다. 계획 미지정은 `null`이며 기존 사진이나 포인트에서 계획을 추측하지 않는다.

## 데이터와 저장

`MaintenanceItem`의 `(planId|null, pointId)`로 안정된 UUID v5를 만든다. 한 pair에는 한 항목만 존재하며 기록 목적을 바꿔도 ID와 관계가 바뀌지 않는다. `photoIds`는 같은 pair에 속한 실제 사진만 선택할 수 있다.

- `repairStatus`: `none`(등록 전), `review`(검토 필요), `planned`(작업 예정), `progress`(작업 중), `done`(완료).
- `repairMethod`: `undecided`(미정), `paint`(도장), `replace`(교체).
- `inWorklist`: 명시적으로 등록한 항목만 워크리스트에 표시한다. 해제는 삭제가 아니며 ID·상태·방법·TA·근거와 이력이 남는다.
- `ta`: TA 포함 여부다. 상태·방법·TA를 바꾸어도 워크리스트 등록 여부는 자동 변경하지 않는다.
- `recordPurpose`: 업무 검사·발표용·검증용을 명시하며 기본 조회는 업무 검사다. 부모 계획·포인트·사진의 목적 변경을 전파하지 않는다.

신규 저장은 `expectedVersion: null`, 기존 수정은 읽은 정수 버전을 전달한다. 수정자와 사유는 필수다. 상태·등록·목적·근거를 한 번에 저장하며 버전 검사와 수정 이력이 같은 트랜잭션에 포함된다. 중복 pair 생성·오래된 버전·잠금 충돌은 409로 반환한다. 통신 장애 뒤에는 실제 저장 상태를 확인하고 재시도해야 한다.

보수 저장은 항목을 잠근 다음 기존·새 근거 사진의 합집합을 정렬해 잠근다. 사진의 계획·포인트 변경도 같은 사진 행을 잠그며, 기존 pair의 보수 참조가 있으면 먼저 근거 선택을 해제하도록 409로 안내한다. 등록 해제·검증 목적·숨김·페이지 밖 항목도 관계 보호 대상이다. 관계 쓰기 트랜잭션만 READ COMMITTED를 사용하며 전역 격리 수준은 바꾸지 않는다.

## API

| 경로 | 계약 |
|---|---|
| `GET /api/maintenance/query` | 전체 COUNT·페이지·포인트 집계를 하나의 반복 읽기 스냅샷으로 반환 |
| `GET /api/maintenance/pair?planId=unassigned&pointId=<UUID>` | 해당 pair의 항목 또는 `null`; 특정 계획은 UUID 사용 |
| `GET /api/maintenance/:id` | 목적·목록 등록 여부와 무관하게 ID로 조회 |
| `GET /api/maintenance/:id/history` | 원래 값·변경값·수정자·시각·사유 |
| `POST /api/maintenance` | pair·신규 버전·업무 값·목적·수정자·사유로 생성 |
| `PATCH /api/maintenance/:id` | pair는 유지하고 CAS로 업무 값·목적 수정 |

목록 필터는 `planId`, `pointId`, `recordPurpose`, `inWorklist=true|all`, `ta`, `repairStatus`, `repairMethod`, `teamId`, `rackId`, `search`, `page`, `pageSize`다. 기본은 업무 검사·등록된 항목·페이지당 50개이며 최대 100개다. 검색은 계획 제목·설비·랙·포인트의 문자 그대로 비교한다. 사진 표시/AI 분류 필터와 보수 업무 필터를 혼용하지 않는다.

## 화면

포인트 상세에서는 특정 계획 또는 계획 미지정을 명시적으로 선택한다. 사진 상세에서는 저장된 계획·포인트의 기록으로 이동한다. 입력 중인 사진 판단이나 포인트 기본정보가 있으면 먼저 저장하도록 이동을 막는다.

보수 편집은 열었을 때의 버전을 유지하며, 폴링이 입력을 덮지 않는다. 실패하면 입력을 유지하고 성공 응답을 받은 뒤에만 새 기준으로 바꾼다. 목록 밖 선택에도 마지막 이름 또는 짧은 식별자와 개별 해제 기능을 제공한다. 숨긴 사진은 근거 관계를 유지하되 원본을 자동 표시하지 않는다. 조회 실패 시 마지막 결과임을 표시한다.

## 기존 자료 이관과 배포 순서

기존 포인트의 `repairStatus`, `repairMethod`, `managed`, `ta`는 원문을 남긴다. 보수 상태의 새 소유자는 MaintenanceItem 하나이며 구형 화면의 포인트 업무 필드 PATCH는 입력을 보관하고 새로고침하라는 422로 거절한다. 새 포인트에는 `maintenanceSchemaVersion: 1`을 기록한다.

`node scripts/migrate-maintenance.mjs`는 이관 예정 수만 확인한다. `--apply`를 명시하면 포인트별로 항목 생성·`maintenanceMigrationVersion: 1`·이력을 한 트랜잭션에 저장한다. 최초 목록 포함은 기존 `managed || ta`이며 상태·방법·TA는 그대로 옮긴다. 계획은 미지정, 근거는 빈 배열로 시작한다. 기존 정상 항목이나 완료된 이관을 덮지 않고, 완료 표식만 있고 대상이 없으면 실패한다. 포인트 원본은 표식·버전·시각 외에 누락 필드를 임의 추가하지 않는다.

배포는 기존 API 쓰기를 멈추고 전체 메타데이터·이력을 보존한 뒤 이관을 완료하고 새 API를 시작한다. 이관 전 기존 포인트의 새 보수 저장은 409로 막아 신규 기본값이 기존 업무 상태를 가리지 않게 한다. 이관은 자동 서버 시작 동작에 포함하지 않는다. 새 보수 기록을 편집한 뒤에는 옛 포인트 쓰기 API를 그대로 재활성화하면 안 된다.

검증 스크립트 `verify-maintenance.mjs`는 별도 smoke 환경과 모델 연결 차단을 명시해야 실행된다. 재시작 검사 도구는 모든 목적과 목록 해제 항목을 포함한 보수 기록·전체 이력을 함께 비교한다. `--metadata-only`는 원본 바이트 검사를 했다는 뜻이 아니다.
