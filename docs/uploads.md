# 파일별 원본 업로드 운영

업로드 화면은 JPG·PNG 파일을 개수나 파일당 20MB로 제한하지 않는다. 파일마다 원본 SHA-256을 증분 계산하고 4MiB 청크로 순서대로 전송한다. 한 파일의 실패가 이미 저장된 파일을 취소하지 않는다. 전송 완료와 AI 판독 완료는 별도 상태다.

## 재시도 계약

- 브라우저의 전송 ID는 파일명·크기·전체 SHA-256·계획/포인트에 고정된다. 같은 ID로 다른 내용을 보내면 409다. 서버는 세션을 만들 때 검사 UUID와 객체 키를 한 번 정한다.
- `POST /api/upload-sessions`로 생성/재조회하고 `GET /api/upload-sessions/:id`로 확정된 offset과 저장 결과를 확인한다. 각 `PUT /:id/chunks?offset=...`에는 `application/octet-stream` 본문과 `X-Chunk-SHA256`을 보낸다. 같은 청크를 다시 보내도 길이와 실제 SHA가 같아야 한다.
- `POST /:id/complete`는 실제 이미지 형식·디코딩·크기·전체 SHA·계획 관계를 검증한 뒤 원본을 보관한다. 같은 ID의 기존 객체는 실제 SHA를 확인해 재사용하며 무조건 덮어쓰지 않는다. 사진·등록 이력·완료 세션은 한 DB 트랜잭션이다.
- DB 커밋 응답이나 객체 저장 응답이 끊겨도 객체를 먼저 삭제하지 않는다. 서버 상태 확인 후 같은 ID로 완료 요청을 반복한다. 미확정 파일 꼬리만 DB의 확정 offset으로 복구한다.
- 브라우저는 전송 메타데이터를 해당 사이트의 localStorage에 보관한다. 새로고침/창 닫기 후 서버 상태부터 조회한다. 아직 받지 못한 바이트를 전송하려면 원래 파일을 다시 선택해야 하며, 전체 SHA가 같을 때만 이어간다. 브라우저 데이터를 지우거나 공유 URL이 바뀌면 이 로컬 전송 목록은 유지되지 않는다. 이미 저장된 사진은 서버 목록에 남는다.
- 24시간 동안 진전이 없는 수신 세션의 임시 파일은 만료된다. 같은 SHA로 `POST /:id/restart`하면 검사 UUID를 보존한 채 처음부터 받는다. 최종 저장 중/완료 상태의 원본을 이 경로로 지우지 않는다. 완료·만료 뒤 남은 임시 파일과 오래된 청크/원시 수신 임시 파일도 정리한다.
- 호환용 `POST /api/inspections` multipart에는 파일 순서에 맞는 UUID 배열 `uploadIds`가 필요하다. 클라이언트는 재요청에도 같은 ID를 사용해야 한다. 승인 demo의 SHA 기반 재사용 경로만 예외다. 새 UI는 이 multipart 묶음 경로를 사용하지 않는다.

## 실행과 저장 공간

API 임시 디렉터리는 `UPLOAD_TEMP_DIR`로 지정한다. 로컬 기본값은 `./uploads/incoming`, Compose는 별도 named volume `api-uploads`를 `/uploads-tmp`에 연결한다. API 컨테이너 교체 때 이 볼륨을 보존한다. 같은 임시 디렉터리에는 API 작성 프로세스 하나만 둔다. 세션별 프로세스 mutex와 DB advisory lock을 함께 사용한다.

전송·원시 수신·썸네일 생성은 임시 디스크를 사용한다. 받은 원본은 재인코딩하지 않으며 썸네일만 별도 작은 이미지로 만든다. 디스크 여유 검사, 동시 최종 저장 제한, 최대 4천만 픽셀의 디코더 보호는 유지한다. 임시 공간·객체 저장소·네트워크가 부족하거나 지원하지 않는 이미지면 파일별 실패를 표시한다. 수량 제한을 없앴다는 뜻이 무한 용량 보장은 아니다.

모델 서비스는 PR #13의 `90dc40209ded6b330552e20079780aa7ac90f635` 또는 그 변경을 포함한 버전이 필요하다. 입력은 기존처럼 완성된 원본 한 장의 multipart `image`이며 업로드 청크나 계획 메타데이터를 모델에 보내지 않는다. 스트리밍 입력 경로만 바꾸고 동결 가중치·전처리·모델 버전은 유지한다.

`compose.model.yaml`은 `model-uploads` 디스크 볼륨을 `/uploads-tmp`에 연결하고 `TMPDIR`로 사용한다. 새 모델 Dockerfile은 이 경로를 UID/GID 10001, 모드 0700으로 준비한다. **새 named volume의 기본 copy-up을 사용하며 `volume.nocopy: true`를 지정하지 않는다.** 기존 볼륨이나 host bind의 소유권을 자동 교정하지 않으므로 기동 시 모델 사용자로 실제 파일 쓰기와 `tempfile.gettempdir()` 경로를 확인한다. Mac 직접 실행도 메모리 파일시스템이 아닌 전용 쓰기 가능한 TMPDIR를 지정한다.

임시 디렉터리·DB·객체·가중치·로컬 전송 검증 기록은 Git과 Docker build context에서 제외한다. 운영 중 `docker compose down -v`로 볼륨을 지우지 않는다. 모델 성능 합격 여부와 새 업로드 기능 검증은 별도로 보고한다.
