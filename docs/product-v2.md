# PlantPilot 제품 개편 설계

2026-09-21 후속 사용자 요구를 반영한 설계·구현 범위다. 제품명은 **PlantPilot / 플랜트파일럿**, 설명은 **검사·보수 통합 관제**로 통일한다. 이 문서는 기능 완료나 실제 실행 성공의 증거가 아니다. 각 항목은 구현 후 같은 버전의 화면·백엔드·실제 파일로 확인한다. 기존 목표와 검증 원칙은 [goal.md](goal.md)를 함께 따른다.

## 1. 적용 범위와 보존 경계

- 계획에서 검사 대상과 사진을 등록하고, 판독 결과를 보수 검토와 워크리스트로 연결하는 흐름을 우선한다. 기존 Next.js·API·MySQL·MinIO·동결 모델 구성을 확장하며 새 플랫폼이나 외부 서비스를 도입하지 않는다.
- 사용자·동료 피드백이 없어도 구현·검증·개선을 진행한다. 에이전트의 실제 브라우저 검증과 실제 사람의 사용 시간·검수 결과는 구분한다.
- **원본 300장의 공유 사이트 공개 허용 여부만 별도 답변 대기 중이다.** 답변 전에는 원본을 공유 서버·DB·객체 저장소·터널에 편입하지 않는다. 원본을 다루는 준비가 필요하면 별도 로컬 환경으로 격리한다. 화면에서만 숨기거나 CORS만 설정하는 것은 공개 차단으로 인정하지 않는다. 실제 팀 경계 답변은 구현의 선행 조건이 아니며, 가상 정유 1~4팀 구역으로 진행한다.
- 팀과 좌표는 가상 설정으로 구현할 수 있다. 원본 사진과 파일명·분리 목록을 보존하고, 가상 배치를 실제 설비 위치 확인으로 표시하지 않는다.
- 기존 train 231 / validation 58 / 고정 test 10 분리와 제외된 동일 내용 중복 1장을 유지한다. 복제·등록·가상 배치를 새 학습 표본으로 집계하지 않는다. 일반 업로드를 자동 학습에 편입하지 않는다.
- 현재 동결 모델과 전처리, 기존 train 99.57% PASS / test 60% FAIL을 유지한다. 고정 test를 다시 추론·평가하거나 배치·튜닝용으로 읽지 않는다. 새 모델 학습·서비스 모델 교체는 이번 화면 개편의 작업이 아니다.
- ‘전체 사진 균등 배치’ 요구를 고정 test 재실행으로 구현하지 않는다. 원본 전체의 공개와 고정 test를 포함한 시연 범위가 정리되기 전에는 해당 전체 요구를 완료로 표시하지 않는다. 승인된 비-test 자료의 가상 배치와 동결 모델 연결을 먼저 구현·검증한다.
- 새 비용, 외부 전송 목적지, 계정 권한 확대, 중요한 원본 삭제는 기존 판단 경계를 유지한다. 코드와 공개 가능한 기록만 승인된 작업 브랜치로 게시하며, 원본·DB·가중치·로컬 상태·비밀은 Git에 넣지 않는다.

## 2. 요구사항과 결과 화면

| ID | 사용자 요구 | 구현할 동작과 경계 |
|---|---|---|
| R01 | InspectLoop 이름 교체 | 헤더·사이드바·페이지 제목·접근성 이름·푸터의 제품명을 PlantPilot / 플랜트파일럿으로 통일한다. 제품 설명은 ‘검사·보수 통합 관제’로 쓴다. 과거 실행 기록의 당시 이름은 소급 변경하지 않는다. |
| R02 | 글자 크기와 균형 개선 | 본문·표·입력·보조 설명·KPI의 크기와 간격을 함께 조정한다. 큰 제목만 키우지 않으며 실제 화면 배율에서 잘림·겹침·과도한 밀도를 확인한다. |
| R03 | 대시보드 KPI 클릭 | 모든 KPI가 해당 조건을 적용한 목록으로 이동한다. 카드 숫자와 이동 후 전체 건수가 같은 집계 기준을 사용하고, 선택한 계획·팀·기간 등 표시된 조건을 유지한다. |
| R04 | 업로드 시연 선택 제거 | 최종 제품의 업로드 화면은 로컬 파일 선택을 제공하고 demo 선택 버튼과 시연 전용 안내를 제거한다. 승인 demo 파일은 내부 검증 자료로 보존할 수 있으나 최종 업무 자료로 자동 노출하지 않는다. |
| R05 | 10장·20MB 고정 제한 제거 | 선택 개수와 파일당 20MB의 임의 제한을 없애고 파일별 대기열·청크 전송·디스크 임시 수신·부분 실패 재시도로 처리한다. API와 모델 서비스의 기존 20MB 제한을 함께 개선한다. 모든 크기의 파일이 자원과 무관하게 성공한다고 약속하지 않는다. |
| R06 | 기술 문구 제거 | 기본 업무 화면은 계획·사진·판독·보수·저장 상태와 다음 행동에 집중한다. 서버 구성·내부 경로·개발 상태 같은 설명은 실행 문서로 옮긴다. 공개 사진의 조회 가능 범위, 실패·미확정 등 사용자의 판단에 필요한 안내는 유지한다. 모델 버전·전처리·성능 미달은 API와 검증 기록에 보존한다. |
| R07 | 최근 사진 유지와 상세 삭제 | 대시보드의 최근 사진 영역은 유지한다. 사진 상세에 복구 가능한 삭제를 제공하고, 숨긴 사진을 다시 찾아 같은 ID로 복원할 수 있게 한다. 실제 원본·MinIO 객체·AI 결과·수정 이력을 지우지 않는다. |
| R08 | 지도 확대·시각 품질 개선 | 첨부 Google Earth 화면과 `ref/3d map.png`를 참고해 배경을 보강하고 확대·선택이 가능한 지도를 만든다. AI로 보강한 배경과 가상 배치가 실제 측량·설비 식별 결과는 아님을 구분한다. 제공 그림의 출처 표시는 보존한다. |
| R09 | 정유 1~4팀 → 파이프랙 → 포인트 | 가상 팀 4개 아래 랙과 포인트를 안정 ID로 연결한다. 팀·랙을 선택하면 해당 대상과 사진 수를 확인하고 포인트 상세로 이동한다. 목록 순서나 새 등록 때문에 기존 위치가 움직이지 않게 한다. |
| R10 | 계획에서 포인트·사진 등록 | 계획 작성·상세에서 기존 포인트를 연결하거나 새 포인트를 등록하고 사진을 추가한다. 계획 저장 자체와 사진 저장·AI 완료 상태를 구분한다. 사진 실패가 이미 저장한 계획·포인트를 사라지게 하지 않는다. |
| R11 | 사진 탭의 계획별 매칭 | 사진은 계획별로 묶거나 필터링하며 해당 계획·포인트를 명확히 표시한다. 같은 포인트의 서로 다른 계획에 속한 사진을 혼합하지 않는다. 기존 자료의 계획은 이름·날짜로 추측하지 않고 ‘계획 미지정’으로 남긴다. |
| R12 | 보수 검토와 작업 방법 | 사진 판독을 근거로 보수 검토를 기록하고 상태와 방법을 별도로 선택한다. 업무 상태는 ‘검토 필요·작업 예정·작업 중·완료’, 미등록은 ‘등록 전’으로 구분하고 방법은 ‘미정·도장·교체’다. 숫자 등급만으로 작업 방법이나 실제 보수 완료를 확정하지 않는다. |
| R13 | 명시적인 워크리스트 | 보수 검토 항목을 워크리스트에 저장·해제하고 별도 화면에서 모아 조회한다. 원래 계획·포인트·근거 사진으로 돌아갈 수 있으며 기존 TA 포함 여부도 보존한다. 해제는 보수 기록 삭제가 아니다. |
| R14 | 최종 화면에서 실험 자료 제외 | `recordPurpose`와 `visibility`를 백엔드에서 적용해 검증용 자료를 기본 목록·최근 사진·지도·KPI에서 일관되게 제외한다. 파일명이나 제목에 demo/validation이 들어갔다는 이유로 분류하지 않는다. |
| R15 | 전체 사진의 균등 가상 배치와 실제 모델 시연 | 승인된 대상 자료를 안정된 식별자·해시로 관리하고 팀·랙·포인트에 가상으로 배치한다. 배치 대응을 저장하고 원본은 보존한다. 새 시연 사진은 동결 모델을 실제 호출하며 파일명 정답을 예측값으로 반환하지 않는다. 원본 공개와 고정 test 경계가 미확정인 부분은 별도 미완료로 보고한다. |

로컬 파일 선택은 브라우저의 표준 파일 선택기를 사용한다. 브라우저·OS가 특정 폴더를 자동으로 열거나 과거 선택 위치를 항상 기억한다고 보장하지 않는다. 임의 로컬 경로를 서버에 보내 파일을 읽게 하는 방식은 사용하지 않는다.

## 3. 데이터 계약

기존 `entities`와 `history` 구조를 사용한다. 필요한 엔터티·관계와 API 필드를 추가하되 전면적인 DB 교체는 하지 않는다. 모든 업무 변경은 안정 ID, 수정 버전, 수정자·시각·사유·전후 값을 보존한다.

| 대상 | 최소 계약 | 일관성 규칙 |
|---|---|---|
| Team / Rack / Point | Team: `id`, `name`. Rack: `id`, `teamId`, `name`. Point: `id`, `rackId`, 기존 설비번호·이름, 가상 좌표와 `locationSource` | 초기 팀은 정유 1~4팀의 가상 설정이다. 좌표는 저장된 배경 기준 상대 좌표로 관리하고 `locationSource: virtual`을 명시한다. 미확인 위치는 임의 실제 좌표로 채우지 않는다. |
| Plan / PlanPoint | Plan: 기존 계획 필드와 중복 없는 `pointIds`. PlanPoint는 `planId`, `pointId`의 논리적 연결 | 한 계획에 여러 포인트, 한 포인트에 여러 계획을 연결할 수 있다. 기존 JSON 저장 구조에서 `pointIds`로 구현할 수 있으며 별도 테이블을 강제하지 않는다. 기존 `plan.pointId`는 명확한 경우 해당 연결로 옮기고 호환 응답·원래 이력을 보존한다. |
| Photo | `id`, `planId`, `pointId`, `objectKey`, 원본 SHA-256·크기·형식, AI 상태·원결과, 사람 수정값, 재촬영·라벨링 후보, `editVersion` | 신규 계획 흐름에서는 두 ID를 함께 저장하고 해당 PlanPoint 연결을 검증한다. 기존 `planId: null` 자료는 미지정으로 유지한다. AI와 사람 수정값을 분리하고 사진의 계획·포인트 변경도 이력을 남긴다. |
| MaintenanceItem | `id`, `planId`, `pointId`, 근거 `photoIds`, `repairStatus`, `repairMethod`, `inWorklist`, `ta`, 사유·수정 버전 | 같은 계획·포인트의 업무 기록을 화면 간 공유한다. 상태·방법·워크리스트 포함 여부는 각각 독립적이며 중복 저장을 방지한다. 기존 포인트의 보수 상태·관리·TA 값은 유실 없이 이관한다. 포인트 화면의 요약과 워크리스트가 따로 보수 상태를 소유하지 않는다. |
| 표시 목적과 삭제 | `recordPurpose`: `inspection / presentation / verification`, `visibility`: `visible / hidden`, `hiddenAt / hiddenBy / hiddenReason` | 검증용 자료는 명시적으로 분류한다. `presentation`도 공개 허용을 뜻하지 않는다. 사진 삭제는 숨김이며 복원 시 같은 ID·원본·이력을 유지한다. 숨긴 사진에 진행 중 AI 결과가 도착해도 자동으로 다시 표시하지 않는다. |
| 원본 대응 | `sourceId`, `sourceSha256`, 가상 배치 대응 | 기존 원본 식별자·해시를 보존하며 파일명에서 위치나 예측을 만들지 않는다. 시연 복제본과 원본의 대응은 새 학습 표본 생성과 구분한다. 민감한 원본 대응 정보는 공개 API·Git에서 제외한다. |

계획·포인트·사진 관계는 API에서 검증한다. UI 선택값만 믿지 않으며, 다른 계획의 사진을 보수 항목에 묶는 등 관계가 어긋난 요청은 거절한다. 새 계획 저장 후 포인트 연결·사진 등록이 일부 실패하면 완료된 결과와 실패 항목을 구분해 복구한다.

계획의 팀·랙 선택은 기본 입력 문맥이다. 다른 랙의 포인트도 명시적으로 추가할 수 있고 화면에 각 팀·랙을 표시하며, 모든 포인트가 같은 랙이라고 잘못 확정하지 않는다. 실제 소속은 Point → Rack → Team으로 조회한다. 새 포인트 생성 후 계획 연결이 충돌하면 생성된 포인트를 보존하고 최신 계획에 재연결할 수 있게 안내한다. 기존 사진·이력의 관계는 선택 없이 자동 변경하지 않는다.

표시 목적·숨김과 **외부 접근 허용 여부는 다른 계약**이다. 기본 목록에서 숨겨도 직접 이미지 URL이나 ID 조회로 접근 가능하면 비공개가 아니다. 승인 전 원본은 별도 로컬 DB·버킷·API에 격리하고 공유 환경에서 접근할 경로를 만들지 않는다.

목록·KPI·지도·최근 사진은 같은 백엔드 필터를 사용한다. 페이지에 로딩된 일부 항목만 세어 전체 건수로 표시하지 않는다. 현재 최신 1,000개 조회 한계가 새 업로드를 조용히 누락하지 않도록 페이지 조회와 전체 집계를 분리한다. 삭제·복원·워크리스트 해제 후에도 이 기준을 유지한다.

## 4. 업로드와 실제 추론 계약

1. 사용자가 계획·포인트와 파일들을 선택하면 파일별 전송 식별자를 부여한다. 재시도는 같은 식별자를 사용하고, 사용자가 별도로 새 등록한 동일 파일은 재시도와 구분한다. SHA만으로 모든 검사 기록을 하나로 합치지 않는다.
2. 브라우저는 순차 대기열로 전송한다. 큰 파일은 정해진 크기의 청크로 나누며 한 파일이나 한 요청의 실패가 나머지 성공 항목을 취소하지 않는다. 진행률과 저장 완료·AI 대기·판독 완료·실패 상태를 구분한다.
3. 서버는 청크를 메모리에 전부 모으지 않고 임시 디스크로 받는다. 서버가 생성한 임시 ID·오프셋·수신 크기를 검증하며 사용자 파일명·로컬 경로를 저장 경로로 사용하지 않는다. 임시 파일 정리와 기존 원본 삭제를 구분한다.
4. 완성된 파일의 실제 형식·디코딩 가능 여부·크기·SHA를 확인한 뒤 MinIO 원본과 DB 기록을 연결한다. **원본 재인코딩·압축·축소로 제한을 우회하지 않는다.** 썸네일은 별도 파생물로 만들고 원본 SHA를 유지한다.
5. 재요청은 업로드 식별자로 저장 결과를 조회해 응답 손실 뒤 중복 기록을 만들지 않게 한다. 부분 수신·취소·실패·최종 저장 상태를 구분하고, 실패한 항목만 복구한다. 저장 성공이 불확실하면 이미 저장된 원본을 먼저 삭제하지 않는다.
6. 제품 API와 모델 서비스의 고정 20MB 제한을 함께 변경한다. 모델도 파일 기반 수신·처리로 대용량 원본을 받되, 동결된 EXIF/RGB/이미지 크기 변환·정규화·모델 버전을 유지한다. 새로운 입력 경로의 기존 승인 사진 결과가 동결 계약과 일치하는지 확인한다.
7. 디스크 부족·연결 중단·읽을 수 없는 이미지 등 실제 실패는 파일별로 안내한다. 청크·동시 처리 수와 디코더 자원 보호는 유지하되 이를 다시 ‘사용자는 10장/20MB까지만’이라는 제품 제한으로 만들지 않는다. 수량·용량 제한 제거를 무한 저장 공간이나 모든 형식 지원으로 표현하지 않는다.

사진의 실제 저장 완료와 모델 처리 완료는 별도다. 저장된 원본과 같은 사진 ID를 큐에서 처리하고, AI 실패 재시도는 새 원본·새 검사 기록 생성 없이 기존 이력에 이어 기록한다.

## 5. 지도·자료 표시와 사용자 화면

- 지도 배경의 AI 보강은 시각적 가독성과 확대 표현에 한정한다. 추정한 설비·경계를 사실로 확정하지 않으며 실제 팀 경계 답변 전에는 가상 팀 구역을 사용한다.
- 팀 → 랙 → 포인트 선택과 계획·사진 필터가 같은 ID로 연결된다. 고정된 12개 표시나 배열 순서에 따른 위치 변화로 대상이 사라지지 않게 한다. 여러 대상을 한 번에 표현하기 어려우면 단계별 선택으로 전체에 접근하게 한다.
- 균등 배치는 등급·정답·test 결과를 사용하지 않고 승인 대상의 안정 ID 순서와 저장된 배치표로 정한다. 대상 수가 바뀌어도 이미 저장한 배치를 임의로 다시 섞지 않는다. 팀·랙별 배치 수와 미배치 수를 확인할 수 있게 한다.
- 최근 사진은 유지하며 현재 계획·표시 목적·숨김 조건을 따른다. 상세 삭제 후 목록·KPI·지도에서 제외되고, 복원하면 같은 사진·계획·포인트·AI·사람 판단·이력으로 돌아온다.
- 모든 KPI의 제목·숫자·도착 목록 조건을 대응시킨다. 보수 검토, 실제 작업 방법 선택, 워크리스트 저장은 구분하고 기본 화면에는 사용자가 수행할 행동을 한국어로 표시한다.
- 기존 demo/validation 자료를 파일명으로 제거하지 않는다. 명시적으로 검증용임이 확인된 기록을 분류하고, 일반 사용자가 등록한 유사 이름의 사진은 보존한다. 최종 화면 정리는 데이터·학습 분리 목록 삭제가 아니다.

## 7. 실제 Done과 증거

각 검사는 사용 커밋·빌드·환경·입력 수/크기·시작/종료 정의를 기록한다. 새 화면과 변경된 저장·업로드 경로는 새로 검증한다. 기존 성공 기록은 회귀 판단의 근거이며 새 구현의 실행 결과로 대신하지 않는다.

| D09 | 새 전체 업무 흐름을 처음부터 수행 | 계획 생성 → 대상 등록/연결 → 사진 선택/저장 → 판독 확인 → 보수·워크리스트 저장 → 이력 재조회 구간을 새로 계측. AI 결과만 기다린 구간을 별도로 남기고, 그동안 수행한 다른 업무는 이중 차감하지 않음. 에이전트 조작 약 1분 판정과 사람 시간 미측정을 구분함. |
| D10 | 변경 데이터가 있는 상태에서 정상 재시작 후 재조회 | 사진·계획 연결·보수 방법·워크리스트·숨김 상태·업로드 복구 정보·AI와 사람 값·전체 이력 및 원본 SHA 보존. 볼륨·원본을 삭제하지 않음. |
| D11 | 입력 경로 변경 전후 동결 모델 계약 확인 | 기존 승인 사진의 원본 바이트, 모델·전처리 버전·동결 가중치 계약, 실제 결과 비교. 고정 test 재실행 없음. 기존 train/test 결과와 새 기능 검사·가상 배치를 혼합하지 않음. |

기존 10장 업로드 30초·10장 판독 3분 기준은 **성능 측정 표본**으로 유지하며 업로드 수량 제한으로 사용하지 않는다. 새 12장 이상·대용량 입력에는 실제 파일 수·바이트·시간을 별도로 보고한다. 전체 약 1분은 AI 판독 대기 제외 기준이며, 하위 구간 통과만으로 전체를 통과 처리하지 않는다. 단 한 번의 실행을 모든 네트워크·부하·사용자의 성능 보장으로 확대하지 않는다.

전체 화면·업로드 경로의 변경 결과, 아직 답변 대기 중인 원본 공개, 실제 경계를 확인하지 않은 가상 배치의 한계, 모델 test 60% 미달은 각각 보고한다. 이 설계 문서가 작성됐다는 이유로 어느 기능도 PASS로 표시하지 않는다.
